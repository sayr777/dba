# Уровни изоляции транзакций (Transaction Isolation)

Уровень изоляции определяет, какие изменения параллельных транзакций видит текущая транзакция; в PostgreSQL четыре уровня, но фактически реализованы три модели поведения, а `Read Uncommitted` работает как `Read Committed`.

---

## 1. ACID и изоляция

- **Atomicity** — транзакция выполняется целиком или не выполняется.
- **Consistency** — данные переходят из одного согласованного состояния в другое.
- **Isolation** — параллельные транзакции не видят незавершённых изменений друг друга.
- **Durability** — после `COMMIT` изменения переживают сбой.

Изоляция — это компромисс между строгостью и параллелизмом. Чем строже уровень, тем больше блокировок и откатов.

---

## 2. Аномалии

| Аномалия | Что происходит |
|---|---|
| **Грязное чтение** | Транзакция читает данные, которые другая транзакция ещё не зафиксировала |
| **Неповторяемое чтение** | Повторный `SELECT` в той же транзакции возвращает другие данные |
| **Фантомное чтение** | Повторный запрос возвращает новые строки, которых не было |
| **Потерянное обновление** | Две транзакции перезаписывают изменения друг друга |
| **Write skew** | Две транзакции читают одни данные, принимают решения и вместе нарушают инвариант |

---

## 3. Матрица уровней

| Уровень | Грязное чтение | Неповторяемое | Фантомы | Сериализация |
|---|:---:|:---:|:---:|:---:|
| Read Uncommitted | Невозможно* | Возможно | Возможно | Возможно |
| **Read Committed** (по умолчанию) | Невозможно | Возможно | Возможно | Возможно |
| Repeatable Read | Невозможно | Невозможно | Невозможно** | Возможно |
| Serializable | Невозможно | Невозможно | Невозможно | Невозможно |

\* PostgreSQL не реализует грязное чтение: `Read Uncommitted` ведёт себя как `Read Committed`.  
\** PostgreSQL устранил фантомы на `Repeatable Read` через MVCC, хотя стандарт SQL их допускает.

---

## 4. Как это работает внутри

PostgreSQL использует **MVCC**: каждая транзакция видит снимок данных на определённый момент.

- `Read Committed`: новый снимок на каждый запрос. Поэтому два одинаковых `SELECT` могут вернуть разные данные.
- `Repeatable Read`: снимок на всю транзакцию. Повторные чтения стабильны.
- `Serializable`: снимок + отслеживание конфликтов (SSI). При обнаружении опасного пересечения одна транзакция откатывается с `serialization_failure`.

---

## 5. Практические примеры

### Неповторяемое чтение

```sql
-- T1
BEGIN;
SELECT price FROM products WHERE id = 1;  -- 1000

-- T2
UPDATE products SET price = 2000 WHERE id = 1;
COMMIT;

-- T1
SELECT price FROM products WHERE id = 1;  -- 2000 при Read Committed
COMMIT;
```

На `Repeatable Read` T1 увидит 1000 в обоих запросах.

### Write skew

```sql
-- Правило: хотя бы один врач должен быть на смене.
-- T1 и T2 одновременно читают «на смене 1 врач» и оба уходят.
-- Read Committed / Repeatable Read: правило нарушено.
-- Serializable: одна транзакция откатится.
```

---

## 6. Когда какой уровень

| Сценарий | Уровень |
|---|---|
| Обычный OLTP | `Read Committed` |
| Отчёт по состоянию на момент запуска | `Repeatable Read` |
| Финансовые инварианты, бронирования | `Serializable` |
| Долгие аналитические чтения | `Repeatable Read` + `statement_timeout` |

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
-- ...
COMMIT;

SHOW transaction_isolation;
```

---

## 7. Ошибки и их обработка

На `Serializable` приложение должно уметь повторить транзакцию:

```text
ERROR: could not serialize access due to read/write dependencies among transactions
SQLSTATE: 40001
```

Правило: **повторить всю транзакцию**, а не отдельный запрос. Не ставьте `Serializable` глобально: это увеличит число откатов и потребует retry-логики во всех сервисах.

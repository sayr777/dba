# Регламент резервного копирования

**Источник:** лаб. 03 — «Резервное копирование и восстановление»  
**Кто создаёт:** системный аналитик совместно с DBA  
**Назначение:** фиксирует стратегию бэкапов: типы, частоту, форматы, сроки хранения, RPO/RTO

---

## Зачем этот документ

Без письменного регламента бэкапы делаются «как придётся». Документ превращает неформальное знание в проверяемый процесс. Используется при аудите и при восстановлении после инцидента.

> **Запомнить:** RPO — сколько данных можно потерять. RTO — сколько времени можно восстанавливаться. Регламент должен явно закрывать оба показателя.

---

## Шаблон регламента

```markdown
# Регламент резервного копирования — eshop

## Цели
- RPO: не более 1 часа (допустимая потеря данных)
- RTO: не более 4 часов (максимальное время восстановления)

## Расписание

| Тип               | Инструмент         | Частота    | Хранение | Назначение                        |
|-------------------|--------------------|------------|----------|-----------------------------------|
| Физический бэкап  | pg_basebackup      | Ежедневно  | 7 дней   | Полное восстановление сервера     |
| Логический бэкап  | pg_dump -Fc        | Ежедневно  | 14 дней  | Восстановление отдельных объектов |
| WAL-архивирование | archive_command    | Непрерывно | 7 дней   | PITR (восстановление на момент)   |
| Глобальные объекты| pg_dumpall --globals | Еженедельно| 4 недели | Роли, tablespace                  |

## Хранение
- Бэкапы хранятся на отдельном сервере / S3
- Шифрование: AES-256 (openssl или pgcrypto для логических)
- Доступ: только DBA и руководитель направления

## Проверка (тестирование)
- Ежемесячно: тестовое восстановление из физического бэкапа
- После каждого изменения схемы: pg_restore в dev-среду

## Ответственные
- DBA: выполнение бэкапов, мониторинг
- Аналитик: согласование RPO/RTO с бизнесом
```

## Команды для запоминания

### pg_dump — логический бэкап

```bash
# Custom-формат (рекомендуется): сжатый, поддерживает параллельное восстановление
pg_dump -U postgres -Fc eshop > eshop_$(date +%Y%m%d).dump

# Plain SQL (для чтения вручную):
pg_dump -U postgres eshop > eshop_$(date +%Y%m%d).sql

# Только схема:
pg_dump -U postgres -s eshop > eshop_schema.sql

# Только данные:
pg_dump -U postgres -a eshop > eshop_data.sql
```

### pg_restore — восстановление из Custom-формата

```bash
# Восстановить в существующую БД:
pg_restore -U postgres -d eshop_restore eshop_20241001.dump

# С параллелизмом (быстрее на больших БД):
pg_restore -U postgres -d eshop_restore -j 4 eshop_20241001.dump

# Только одну таблицу:
pg_restore -U postgres -d eshop_restore -t orders eshop_20241001.dump
```

### pg_basebackup — физический бэкап

```bash
# Сделать физический бэкап в папку:
pg_basebackup -U postgres -D /backups/base -Ft -z -P

# -Ft = tar-формат, -z = gzip, -P = прогресс
```

---

## Что запомнить по форматам

| Формат   | Ключ     | Плюс                        | Минус                              |
|----------|----------|-----------------------------|-------------------------------------|
| Plain    | `-Fp`    | Читается человеком          | Нельзя pg_restore, большой          |
| Custom   | `-Fc`    | Сжат, параллельный restore  | Бинарный, только pg_restore         |
| Directory| `-Fd`    | Параллельный dump            | Много файлов, сложнее хранить       |
| Tar      | `-Ft`    | Один архивный файл          | Нет параллельного restore           |

> **Правило**: для производственных бэкапов всегда `-Fc`. Plain только для отладки и переноса.

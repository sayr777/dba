# pgbench

Встроенная утилита PostgreSQL для синтетического нагрузочного тестирования, измерения пропускной способности (TPS), задержек (latency) и валидации настроек пула соединений.

---

## 1. Назначение для системного аналитика

`pgbench` позволяет смоделировать реальный профиль нагрузки на проектируемую базу данных до ввода системы в эксплуатацию:
- определить предельное число параллельных сессий без деградации производительности;
- измерить эффект от внедрения пулера соединений [[tools/pgbouncer]];
- проверить влияние индексов и настроек буферного пула (`shared_buffers`) на транзакционную производительность;
- предоставить измеримые числовые данные для [[artifacts/pgbouncer-justification|обоснования модернизации программно-аппаратного обеспечения]].

В рамках [[course/rpd|РПД «Администрирование баз данных»]] тема относится к **ПК-1-И-26** (Тема 7, 9, Лаб. 07).

## 2. Инициализация тестовой схемы

Перед запуском теста `pgbench` создает 4 стандартные таблицы (`pgbench_accounts`, `pgbench_branches`, `pgbench_tellers`, `pgbench_history`):

```bash
# Инициализация с масштабным коэффициентом (scale factor) s = 50
# scale 1 = 100 000 счетов (~15 МБ), scale 50 = 5 000 000 счетов (~750 МБ)
pgbench -i -s 50 -h localhost -p 5432 -U postgres eshop_bench
```

Флаги инициализации:
- `-i` — создать таблицы и заполнить их начальными данными;
- `-s <число>` — коэффициент масштабирования (размер выборки данных);
- `--foreign-keys` — создать внешние ключи между таблицами схемы;
- `--index-test-tables` — создать первичные ключи и B-tree индексы.

## 3. Запуск нагрузочного теста

```bash
# Запуск теста: 50 клиентов (-c), 4 потока (-j), длительность 60 секунд (-T)
pgbench -c 50 -j 4 -T 60 -h localhost -p 5432 -U postgres eshop_bench
```

Ключевые параметры запуска:
- `-c <число>` — количество одновременно работающих параллельных клиентов (симуляция пользователей);
- `-j <число>` — число рабочих системных потоков ОС;
- `-T <секунды>` — продолжительность теста по времени (например, 60 или 300 с);
- `-t <число>` — ограничение по числу транзакций на каждого клиента;
- `-S` — режим `SELECT-only` (только чтение, без изменений данных);
- `-N` — транзакции без обновления баланса отделений (снижает contention строк);
- `-f <script.sql>` — запуск пользовательского сценария тестирования вместо стандартного TPC-B.

## 4. Интерпретация результатов тестирования

Типовой отчет `pgbench`:

```text
transaction type: <builtin: TPC-B (sort of)>
scaling factor: 50
query mode: simple
number of clients: 50
number of threads: 4
maximum number of tries: 1
duration: 60 s
number of transactions actually processed: 134210
latency average = 22.351 ms
latency stddev = 8.120 ms
initial connection time = 45.210 ms
tps = 2236.784112 (without initial connection time)
```

Метрики для анализа:
- **TPS (Transactions Per Second):** количество успешно обработанных транзакций в секунду. Чем выше, тем лучше пропускная способность.
- **Latency average:** среднее время ожидания ответа на транзакцию (в мс). Для интерактивных веб-систем целевое значение — < 50–100 мс.
- **Latency stddev:** стандартное отклонение задержки. Высокое значение указывает на резкие скачки времени ответа из-за очередей блокировок или сброса «грязных» буферов контрольной точкой (checkpoint).

## 5. Сравнение производительности: прямое подключение vs PgBouncer

| Метрика | 100 клиентов напрямую к PostgreSQL | 100 клиентов через PgBouncer (pool_mode=transaction) |
|---|---|---|
| **Расход RAM на процессы** | ~1 ГБ (100 backend-процессов по 10 МБ) | ~150 МБ (15 backend-процессов в пуле) |
| **TPS** | ~850 tps (борьба за CPU и spinlocks) | ~3200 tps (эффективное мультиплексирование) |
| **Средняя задержка (latency)** | 118 мс | 31 мс |
| **Ошибки «too many connections»** | Возможны при всплеске | Исключены (клиенты ждут в очереди пулера) |

# pgAudit

Расширение PostgreSQL для детального структурированного аудита операций с данными (DML, DDL, READ, ROLE) в соответствии с требованиями информационной безопасности и 152-ФЗ.

---

## 1. Зачем pgAudit системному аналитику

Штатный механизм логирования PostgreSQL (`log_statement = 'all'`) записывает весь входящий текст запросов сплошным потоком, что приводит к переполнению диска и не позволяет гибко фильтровать чувствительные операции.

`pgAudit` (PostgreSQL Audit Extension) предоставляет:
- детальное журналирование действий привилегированных пользователей;
- аудит доступа к персональным данным (ПДн) по требованиям **152-ФЗ**;
- разделение на **сессионный аудит** (по классам операций) и **объектный аудит** (по конкретным чувствительным таблицам через роли);
- структурированный формат записей в системном журнале для последующего разбора SIEM-системами.

В рамках [[course/rpd|РПД]] тема аудита безопасности формирует результаты обучения по **ПК-1-И-31** и **ПК-3-И-3** (Тема 11, Лаб. 08).

---

## 2. Установка и активация

Расширение требует предварительной загрузки в оперативную память сервера через `postgresql.conf`:

```ini
# postgresql.conf (требует перезапуска службы PostgreSQL)
shared_preload_libraries = 'pg_stat_statements, pgaudit'
```

Активация в конкретной базе данных:
```sql
CREATE EXTENSION IF NOT EXISTS pgaudit;
```

## 3. Режимы аудита

### 3.1. Сессионный аудит (Session Audit)
Логирует все команды заданных категорий, выполняемые пользователями в рамках сессии:

```ini
# Категории событий для аудита:
# READ, WRITE, FUNCTION, ROLE, DDL, MISC, MISC_SET, ALL
pgaudit.log = 'write, ddl, role'

# Логировать параметры запросов (подставляемые значения в Prepared Statements)
pgaudit.log_parameter = on

# Логировать текст запроса в отдельной строке
pgaudit.log_statement_once = off
```

### 3.2. Объектный аудит (Object Audit)
Позволяет логировать только обращения к конкретным таблицам, не создавая избыточного шума в логах. Реализуется через специальную роль-маркер:

```sql
-- 1. Создаем роль для аудита (без права входа)
CREATE ROLE auditor_pgaudit NOLOGIN;

-- 2. Указываем pgAudit отслеживать эту роль в postgresql.conf:
-- pgaudit.role = 'auditor_pgaudit'

-- 3. Назначаем права роли auditor_pgaudit на чувствительную таблицу
-- Теперь любое чтение или запись в customers будет зафиксировано в журнале!
GRANT SELECT, UPDATE, DELETE ON customers TO auditor_pgaudit;
```

---

## 4. Формат записи в журнале

Каждая запись аудита маркируется тегом `AUDIT: SESSION` или `AUDIT: OBJECT` и содержит строго определенные поля:

```text
2026-10-29 14:15:22 MSK [12450]: [3-1] user=analyst_ivanova,db=eshop LOG:  AUDIT: OBJECT,1,1,READ,SELECT,TABLE,public.customers,"SELECT customer_id, full_name, email FROM customers WHERE region = 'Central'",<not logged>
```

Поля строки аудита:
1. Тип аудита (`SESSION` или `OBJECT`);
2. Номер оператора в транзакции;
3. Номер подкоманды;
4. Класс команды (`READ`, `WRITE`, `DDL` и т.д.);
5. Команда SQL (`SELECT`, `INSERT`, `ALTER TABLE`);
6. Тип объекта (`TABLE`, `INDEX`, `FUNCTION`);
7. Полное имя объекта (`public.customers`);
8. Текст SQL-запроса;
9. Параметры запроса (если включен `pgaudit.log_parameter`).

## 5. Роль аналитика при аудите ИБ

Системный аналитик:
1. Выделяет перечень таблиц и атрибутов, содержащих персональные данные субъектов (ФИО, телефон, паспорт, адрес доставки).
2. Заполняет [[artifacts/security-checklist|Чек-лист информационной безопасности]].
3. Составляет для DBA матрицу аудита: *какие таблицы и операции подлежат обязательному журналированию* для выполнения требований регуляторов (ФСТЭК / 152-ФЗ).

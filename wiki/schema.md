# Wiki Schema — DBA Course Knowledge Base

Этот документ — **конфигурационный файл для LLM**. Он говорит тебе, как обслуживать эту wiki: как принимать новые источники, как отвечать на вопросы, как обновлять страницы, как развивать саму схему.

Читай этот файл первым при каждой работе с wiki.

---

## 1. Контекст и аудитория

**Курс:** «Администрирование баз данных», 09.03.03, 4 курс, очная форма.  
**Аудитория курса:** системные аналитики — не DBA, не разработчики. Всё, что ты пишешь, должно быть полезно аналитику, работающему в команде с DBA.  
**Стек:** PostgreSQL + Flyway + DBeaver + PgBouncer + pgBadger + psql.  
**Сквозной проект:** БД `eshop` (customers, products, orders, order_items).  
**Язык wiki:** русский. Технические термины, имена команд и идентификаторы — на языке оригинала.

## 2. Два слоя: sources и wiki

```
sources/          ← НЕЛЬЗЯ редактировать
  lectures/lec_01…lec_13/
  labs/lab_01…lab_10/
  docs/exam.md
  docs/reports.md
  README.md

wiki/             ← только здесь ты работаешь
  schema.md       ← этот файл
  index.md        ← каталог всех страниц
  log.md          ← append-only лог изменений
  glossary.md
  concepts/
  tools/
  procedures/
  roles/
  artifacts/
  course/
  cheatsheets/
```

**Правило:** никогда не изменяй файлы из `sources/`. Если источник устарел или ошибочен — добавь примечание в wiki, не правь источник.

## 4. Соглашения по формату страниц

### 4.1. Обязательная структура

Каждая wiki-страница должна содержать:

1. **Заголовок H1** — название концепции/инструмента/процедуры.
2. **Одна строка-резюме** сразу после заголовка (не раздел, просто абзац) — что это и зачем.
3. **Тело** — разделы H2/H3, нумерация или списки, таблицы, примеры кода.
4. **Блок источников** в конце — `> **Источники:** [[lec_NN]], [[lab_NN]]`.
5. **Связанные страницы** — `> **Связанные страницы:** [[concepts/X]], [[procedures/Y]]`.

### 4.2. Ссылки

- Внутренние wiki-ссылки: `[[путь/от/корня-wiki]]` — например `[[concepts/wal-mvcc]]`. Путь без расширения `.md`.
- Ссылки на источники: `[[lectures/lec_03]]`, `[[labs/lab_09]]`.
- Если нужен отображаемый текст: `[[concepts/wal-mvcc|WAL и MVCC]]`.
- Внешние ссылки: обычный Markdown `[текст](https://...)`.

### 4.3. Код

Всегда указывай язык в fence-блоках:

```
```sql
```bash
```toml
```ini
```markdown
```mermaid
```

### 4.4. Таблицы

Выравнивай колонки пробелами для читаемости в raw-виде:

```markdown
| Колонка 1 | Колонка 2 | Колонка 3 |
|-----------|-----------|-----------|
| значение  | значение  | значение  |
```

### 4.5. Чего не делать

- Не копируй большие куски текста из источников — **синтезируй**.
- Не пиши «в этом файле рассматривается...» — пиши суть сразу.
- Не добавляй раздел «Введение» с пересказом очевидного.
- Не дублируй содержимое glossary.md на страницах понятий — давай ссылку.

## 5. Формат log.md

Лог — append-only. Новые записи добавляются **в начало** файла. Формат записи:

```
## [YYYY-MM-DD] <тип> | <краткое описание>

<опциональный блок: что добавлено/изменено/удалено — пулями>
```

Типы операций:

| Тип      | Когда использовать                                     |
|----------|--------------------------------------------------------|
| `init`   | Первичное создание wiki или крупного раздела           |
| `add`    | Добавление новой страницы или раздела                  |
| `update` | Обновление существующей страницы                       |
| `ingest` | Обработка нового источника (лекция, статья, документ)  |
| `fix`    | Исправление ошибки, устаревшей информации              |
| `schema` | Изменение schema.md                                    |

---

## 6. Формат index.md

`index.md` — каталог, не содержательный документ. Каждая строка:

```markdown
| [Заголовок страницы](путь/от/wiki.md) | Одна строка — что найдёт читатель |
```

Описание должно отвечать на вопрос «зачем мне открывать эту страницу», а не пересказывать заголовок.

При добавлении новой страницы:
1. Добавь строку в соответствующий раздел `index.md`.
2. Если раздела ещё нет — создай заголовок H2.
3. Сохраняй алфавитный или тематический порядок внутри раздела.

## 7. Рабочие процессы (Workflows)

### 7.1. Ingest: добавление нового источника

Когда тебе дают новый материал (лекцию, статью, документ) для добавления в wiki:

1. **Определи тип** — это концепция, инструмент, процедура, артефакт или обзор?
2. **Проверь, нет ли существующей страницы** — найди в `index.md`. Если есть — обновляй, не создавай дубликат.
3. **Синтезируй, не копируй** — выдели ключевые идеи, добавь примеры, объясни связи с уже известным.
4. **Добавь ссылки** — найди 2-3 связанные страницы в wiki и добавь `[[ссылки]]` в обе стороны.
5. **Обнови glossary.md** — добавь новые термины, если появились.
6. **Обнови index.md** и **log.md**.

### 7.2. Query: ответ на вопрос студента/преподавателя

Когда тебя спрашивают о теме курса:

1. Найди релевантные страницы в wiki (начни с `index.md`).
2. Если страница есть — ответь, опираясь на неё; укажи ссылку.
3. Если страницы нет, но тема есть в sources — создай страницу по workflow 7.1, потом ответь.
4. Если в wiki есть противоречие с источником — доверяй источнику, обнови wiki.
5. Ответы ориентируй на роль **системного аналитика** — не DBA, не разработчика.

### 7.3. Update: обновление существующей страницы

При обновлении:

1. Не удаляй живую информацию без причины — сначала пойми, почему она была написана.
2. Если устарело — пометь: `> ⚠️ Актуально для PostgreSQL 14. В версии 17 поведение изменилось: ...`
3. Добавляй, не перезаписывай — новая информация идёт как новый подраздел или примечание.
4. После изменения — запись в `log.md` с типом `update`.

### 7.4. Ingest: полный цикл обработки источника

Один источник может затронуть 10–15 wiki-страниц. Полный цикл:

1. **Прочитай источник целиком** — не по диагонали.
2. **Выдели ключевые идеи** — обсуди с преподавателем, что подчеркнуть (если режим интерактивный).
3. **Создай/обнови страницу-резюме** — тип страницы по разделу 3.
4. **Обойди связанные страницы** — добавь новую информацию как подраздел или примечание туда, где тема уже раскрыта.
5. **Обнови glossary.md** — все новые термины.
6. **Обнови index.md** — добавь новые страницы.
7. **Запись в log.md** с типом `ingest`.

Можно ingesting'ить источники пачкой (batch) или по одному с участием преподавателя. Предпочтительный режим для этого курса — **интерактивный**: преподаватель читает резюме, направляет акценты, согласовывает что добавить.

### 7.5. Query: ответ превращается в wiki-страницу

Когда отвечаешь на вопрос — хороший ответ не должен исчезнуть в истории чата:

1. Найди релевантные страницы (start with `index.md`).
2. Синтезируй ответ с цитатами `[[страница]]`.
3. **Если ответа потребовалось больше 5 предложений** — это сигнал, что теме нужна своя wiki-страница. Создай её.
4. Если ответ — сравнение, анализ, таблица — сохрани как страницу в `concepts/` или `artifacts/`.
5. Открытия и связи, найденные в ходе ответа на вопрос, накапливаются в wiki так же, как ingested-источники.

Форматы ответов: Markdown-страница, сравнительная таблица, Mermaid-диаграмма. Выбирай по смыслу.

### 7.6. Lint: health-check wiki

Запускай по запросу преподавателя или при заметных признаках деградации. Проверяй:

| Проблема                                  | Как обнаружить                                              | Как исправить                              |
|-------------------------------------------|-------------------------------------------------------------|--------------------------------------------|
| Противоречия между страницами             | Сравни утверждения о том же предмете на разных страницах    | Привести к единому, указать источник       |
| Устаревшие утверждения                    | Сверь с sources — не изменилась ли тема в новой лекции      | Пометить `⚠️` или обновить                |
| Orphan-страницы (нет входящих ссылок)     | Найди страницы, на которые никто не ссылается               | Добавить ссылки из связанных страниц       |
| Упомянутые, но не раскрытые концепции     | Ищи `[[ссылки]]` на несуществующие файлы                   | Создать страницу-заглушку или полную       |
| Пробелы в покрытии                        | Сравни тематический план курса с index.md                   | Создать недостающие страницы               |
| Термины в тексте без определения          | Ищи технические слова, которых нет в glossary.md            | Добавить в glossary.md                     |

По итогам Lint — запись в `log.md` с типом `fix` и списком исправленного.

### 7.7. Maintain: плановое обслуживание wiki

Периодически (или когда замечаешь проблемы):

- **Битые ссылки**: проверь, что все `[[ссылки]]` ведут на существующие файлы.
- **Orphan-страницы**: страницы без входящих ссылок — добавь ссылки из связанных страниц.
- **Глоссарий**: проверь, что все термины из страниц есть в glossary.md.
- **Дубликаты**: если два раздела на разных страницах говорят об одном — объедини, оставь ссылку.

## 8. Приоритет аналитика

При любом выборе — спрашивай себя:

> Помогает ли это системному аналитику работать с DBA-командой?

Это значит:
- **Шаблоны и чек-листы** важнее теоретических объяснений.
- **Что сказать DBA** важнее, чем «как DBA это делает внутри».
- **Конкретные примеры из eshop** лучше абстрактных примеров.
- **Типичные ошибки аналитика** — обязательно включать.

## 9. Эволюция schema.md

Этот документ — живой. Обновляй его когда:

- Появился новый тип страниц, которого нет в разделе 3.
- Выяснилось, что какое-то соглашение не работает — измени его.
- Появился новый workflow, которого нет в разделе 7.

После изменения schema.md — запись в `log.md` с типом `schema` и описанием что и почему изменилось.

**Не спрашивай разрешения на мелкие правки schema.md** — улучшай по ходу работы. При значительных изменениях (новый тип страниц, новый workflow) — сообщи преподавателю.

3. Прочитай последние 5 записей log.md — пойми что менялось
4. Прими задачу и следуй workflows из раздела 7

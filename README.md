# Администрирование баз данных

Практический курс для системных аналитиков: научиться работать с DBA в командах — понимать жизненный цикл схемы БД, писать планы и скрипты миграции, применять rollback-стратегии, разворачивать БД локально и сопровождать её в CI/CD.

- **Направление:** 09.03.03 «Прикладная информатика», профиль «Информационные технологии и системная аналитика»
- **Уровень / форма:** 4 курс бакалавриата, очная форма
- **Объём:** 26 лек. + 26 лаб. ч. (недели 1–13)
- **Форма контроля:** зачёт
- **Нормативная основа:** ФГОС ВО 3++ по 09.03.03; профстандарт 06.011 «Администратор баз данных» (приказ Минтруда РФ от 27.04.2023 № 408н)

---

## Зачем это системному аналитику

Системный аналитик проектирует информационные системы и ставит задачи команде разработки. Без понимания слоя данных это приводит к:

- изменениям схемы БД «на лету» — без плана, без rollback, без DBA-review;
- простоям при деплое из-за несогласованных миграций;
- инцидентам с потерей данных, которые разбираются постфактум.

Курс даёт навыки, которые позволяют аналитику **участвовать в DB-процессах на равных с DBA**: составлять migration plan, писать SQL-скрипты для Flyway/Liquibase, проводить review миграций в MR, организовывать rollback и проверять результат.

## Технологии версионирования и миграции БД

### Инструменты

| Инструмент      | Подход к миграциям                               | Rollback                              | Типичное применение          |
|-----------------|--------------------------------------------------|---------------------------------------|------------------------------|
| **Flyway**      | SQL-файлы `V1__description.sql`                  | Forward-only (free); Undo (Teams)     | Java/любой стек; CI/CD       |
| **Liquibase**   | Changesets в XML/YAML/SQL                        | `liquibase rollback` по тегу/дате     | Enterprise; гетерогенные СУБД |
| **sqitch**      | Три скрипта: `deploy` / `revert` / `verify`      | `sqitch revert`                       | DBA-ориентированные команды  |
| **golang-migrate** | Пара `001_up.sql` + `001_down.sql`            | `migrate down N`                      | Go-сервисы; лёгкий CLI       |
| **Atlas**       | Декларативная схема (HCL/SQL); diff авто         | Авто-revert                           | Modern DevOps; schema-as-code |
| **Alembic**     | Python-классы или SQL; `upgrade` / `downgrade`   | `alembic downgrade -1`                | Python/FastAPI/Django        |

### Рекомендованный стек курса: Flyway Community + PostgreSQL

Flyway выбран потому что:
- миграции — чистые SQL-файлы, нет нового DSL;
- легко читать в MR/PR: diff = один файл с понятным именем;
- Community-версия бесплатна и поддерживает PostgreSQL;
- прямая интеграция с DBeaver, Docker, GitHub Actions.

### Конвенция именования файлов (Flyway)

```
V{version}__{description}.sql    # применяется один раз, необратимо
U{version}__{description}.sql    # Undo-скрипт (ручной rollback)
R__{description}.sql             # повторяемый (views, функции)
```

Пример набора файлов для фичи:

```
migrations/
  V1__initial_schema.sql
  V2__add_customers_table.sql
  V3__add_orders_fk.sql
  V4__rename_column_total_to_amount.sql    ← MR с планом миграции
  V5__revert_rename_column.sql             ← forward rollback
```

## Workflow миграции в команде (DBA + Аналитик + Разработчик)

```
1. Аналитик / разработчик
   ├── создаёт ветку feature/add-payment
   ├── пишет migration plan (цель, риски, rollback-план)
   └── пишет V5__add_payment_method.sql

2. MR / Pull Request
   ├── DBA review: SQL, индексы, блокировки, zero-downtime
   └── Аналитик review: соответствие требованиям

3. CI/CD pipeline (после merge)
   ├── flyway migrate → staging
   ├── smoke-тесты
   └── flyway migrate → production

4. Если что-то пошло не так
   ├── Вариант A (preferred) : V6__revert_payment_method.sql → MR → деплой
   ├── Вариант B             : flyway undo (U5-скрипт)
   └── Вариант C (крайний)  : восстановление из резервной копии (PITR)
```

### Паттерны zero-downtime миграций

| Изменение             | Опасный путь                              | Безопасный путь                                                         |
|-----------------------|-------------------------------------------|-------------------------------------------------------------------------|
| Переименовать колонку | `ALTER TABLE RENAME COLUMN` (ломает API)  | 1. добавить новую → 2. двойная запись → 3. мигрировать данные → 4. drop |
| Добавить NOT NULL     | `ADD COLUMN NOT NULL` без дефолта (lock)  | 1. добавить nullable → 2. backfill → 3. `SET NOT NULL`                  |
| Добавить индекс       | `CREATE INDEX` (блокировка таблицы)       | `CREATE INDEX CONCURRENTLY`                                             |
| Удалить таблицу       | `DROP TABLE` сразу                        | 1. убрать из кода → 2. деплой → 3. `DROP TABLE`                        |

### Термины

| Термин                      | Определение                                                                                                          |
|-----------------------------|----------------------------------------------------------------------------------------------------------------------|
| Автовакуум (autovacuum)     | Фоновый процесс PostgreSQL, удаляющий мёртвые версии строк после `UPDATE`/`DELETE` и обновляющий статистику         |
| Базовая резервная копия     | Полная копия кластера данных PostgreSQL, сделанная `pg_basebackup`; отправная точка для PITR                         |
| Горячее резервирование      | Режим работы реплики, при котором она принимает запросы на чтение (hot standby)                                      |
| Дамп (dump)                 | Текстовый или бинарный экспорт схемы и/или данных БД, созданный `pg_dump`                                           |
| Двойная запись              | Паттерн zero-downtime: приложение пишет одновременно в старую и новую колонку/таблицу в период миграции              |
| Инстанс                     | Запущенный экземпляр СУБД (один процесс `postgres`, обслуживающий один кластер БД)                                   |
| Кластер PostgreSQL          | Набор баз данных, управляемых одним экземпляром СУБД и хранящихся в одном `PGDATA`-каталоге                         |
| Контрольная точка           | Момент (`checkpoint`), в который PostgreSQL сбрасывает «грязные» страницы из памяти на диск                         |
| Migration plan              | Документ, описывающий цель, шаги, риски и rollback-стратегию изменения схемы; оформляется до открытия MR            |
| Профстандарт 06.011         | «Администратор баз данных» (приказ Минтруда РФ от 27.04.2023 № 408н); определяет трудовые функции и уровни квалификации |
| Репликация                  | Механизм передачи WAL-изменений с primary-сервера на один или несколько standby-серверов                             |
| Rollback                    | Откат изменений схемы или данных к предыдущему состоянию                                                             |
| Forward rollback            | Предпочтительная стратегия отката: создаётся новая миграция, обращающая нежелательные изменения                      |
| Ролевая модель              | Система управления доступом на основе ролей (RBAC): пользователи наследуют привилегии через роли                     |
| Транзакция                  | Атомарная единица работы с БД; все операции либо применяются целиком (`COMMIT`), либо отменяются (`ROLLBACK`)        |
| Undo-скрипт                 | Файл `U{version}__description.sql`, обращающий изменения конкретной версии миграции (Flyway Teams / ручной режим)    |
| Zero-downtime migration     | Изменение схемы БД без остановки сервиса и без блокировки таблиц на время, заметное пользователям                   |

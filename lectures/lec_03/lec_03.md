## Зачем это системному аналитику

Аналитик не управляет ролями напрямую — это задача DBA. Но именно аналитик формулирует требования: кто должен читать таблицу `customers`, кому можно `INSERT` в `orders`, а кому — только просматривать отчёт. Неточно сформулированные требования приводят к тому, что приложение либо получает избыточные права (риск безопасности), либо слишком узкие (инциденты на проде).

Понимание цепочки аутентификации — `pg_hba.conf` → роль → привилегии — позволяет аналитику самостоятельно диагностировать ошибку `permission denied` или `password authentication failed`, не дожидаясь DBA.

> **Ключевая мысль.** Роль — это не «пользователь в базе». Это учётная запись уровня кластера с набором атрибутов. Привилегии на таблицы выдаются отдельно, и только вместе они дают доступ.

## 2. Роли в PostgreSQL: единая концепция

В PostgreSQL нет отдельных понятий «пользователь» и «группа». Есть одна сущность — **роль** (role). Разница только в атрибутах:

| Аналог           | Способ создания           | Ключевой атрибут |
| ---------------- | ------------------------- | ---------------- |
| Пользователь     | `CREATE USER ...`         | `LOGIN`          |
| Группа / профиль | `CREATE ROLE ... NOLOGIN` | `NOLOGIN`        |

> `CREATE USER` — синтаксический сахар для `CREATE ROLE ... WITH LOGIN`. В PostgreSQL это одна и та же DDL-команда.

Роли существуют **на уровне кластера**, а не отдельной базы. Одна роль может работать в нескольких базах (если ей выданы соответствующие привилегии).

> Подробнее о моделях доступа (DAC, RBAC, ABAC/RLS, MAC) — в статье [Модели управления доступом](../../wiki/concepts/access-control-models.md).

## 3. Атрибуты роли

Атрибуты определяют, что роль **может делать с сервером** — в отличие от привилегий, которые регулируют доступ к объектам БД.

| Атрибут                         | По умолчанию           | Описание                                                      |
| ------------------------------- | ---------------------- | ------------------------------------------------------------- |
| `LOGIN` / `NOLOGIN`             | `NOLOGIN`              | Может ли роль подключаться к серверу                          |
| `SUPERUSER` / `NOSUPERUSER`     | `NOSUPERUSER`          | Суперпользователь обходит все проверки прав — только для DBA  |
| `CREATEDB` / `NOCREATEDB`       | `NOCREATEDB`           | Может ли создавать базы данных                                |
| `CREATEROLE` / `NOCREATEROLE`   | `NOCREATEROLE`         | Может ли создавать другие роли                                |
| `REPLICATION` / `NOREPLICATION` | `NOREPLICATION`        | Право подключаться для репликации                             |
| `BYPASSRLS` / `NOBYPASSRLS`     | `NOBYPASSRLS`          | Обходить политики Row-Level Security                          |
| `INHERIT` / `NOINHERIT`         | `INHERIT`              | Автоматически наследовать привилегии ролей, в которых состоит |
| `CONNECTION LIMIT n`            | `-1` (без ограничений) | Максимум одновременных соединений от этой роли                |
| `VALID UNTIL 'timestamp'`       | без ограничений        | Срок действия пароля / доступа                                |
| `PASSWORD 'secret'`             | без пароля             | Пароль роли (хранится в виде хеша, никогда в открытом виде)   |

### 3.1. Создание ролей

```sql
-- Роль-группа (профиль прав): не может логиниться, только хранит набор привилегий
CREATE ROLE app_readonly NOLOGIN;

-- Пользователь приложения: логинится с паролем, ограничен по соединениям
CREATE ROLE app_user LOGIN PASSWORD 'secret' CONNECTION LIMIT 50;

-- Пользователь-аналитик с ограниченным сроком доступа
CREATE ROLE analyst_ivanova LOGIN PASSWORD 'secret'
  VALID UNTIL '2027-01-01';

-- Роль для CI/CD: только миграции, без постоянного доступа
CREATE ROLE migration_runner LOGIN PASSWORD 'secret'
  CONNECTION LIMIT 3;
```

> **Пароль в DDL.** `CREATE ROLE ... PASSWORD 'secret'` пишет открытый пароль в историю команд и в лог, если включён `log_statement = all`. В production используют `\password` в psql или передают пароль через защищённый секрет-менеджер.

### 3.2. Изменение и удаление роли

```sql
-- Изменить пароль
ALTER ROLE app_user PASSWORD 'newsecret';

-- Заблокировать вход без удаления роли
ALTER ROLE analyst_ivanova NOLOGIN;

-- Закрепить параметры сеанса за ролью
ALTER ROLE analyst_ivanova SET search_path TO reporting, public;

-- Удалить роль (нельзя, если роль является владельцем объектов)
DROP ROLE analyst_ivanova;
```

> **Удаление роли-владельца.** Если роль владеет объектами, перед удалением нужно передать владение:
> ```sql
> REASSIGN OWNED BY analyst_ivanova TO postgres;
> DROP OWNED BY analyst_ivanova;
> DROP ROLE analyst_ivanova;
> ```

### 3.3. Просмотр ролей

```sql
-- Все роли кластера с атрибутами
SELECT rolname, rolcanlogin, rolsuper, rolcreatedb, rolcreaterole,
       rolconnlimit, rolvaliduntil
FROM   pg_roles
ORDER  BY rolname;

-- Мета-команда psql (аналог выше)
\du
```

> **Обратите внимание.** `pg_roles` доступен всем, но пароли (`rolpassword`) находятся в `pg_authid` — системном каталоге, доступном только суперпользователю. Это не случайность: хеши паролей — чувствительные данные.

## 4. Иерархия ролей и наследование

Ключевая идея RBAC в PostgreSQL: **ролям назначаются другие роли** как группы; привилегии наследуются через атрибут `INHERIT`.

```sql
-- 1. Создаём профили прав (группы)
CREATE ROLE app_readonly  NOLOGIN;
CREATE ROLE app_readwrite NOLOGIN;

-- 2. Назначаем профили конкретным пользователям
GRANT app_readonly  TO analyst_ivanova;
GRANT app_readwrite TO app_user;
-- analyst_ivanova автоматически получает все привилегии app_readonly
```

```
Кластер
├── app_readonly   (NOLOGIN) ←── профиль: только чтение
│     ├── analyst_ivanova (LOGIN) — наследует через INHERIT
│     └── analyst_petrov  (LOGIN) — наследует через INHERIT
├── app_readwrite  (NOLOGIN) ←── профиль: чтение + запись
│     └── app_user (LOGIN, CONNECTION LIMIT 100)
└── postgres (SUPERUSER, LOGIN) — только для DBA
```

**Почему это важно для аналитика:** чтобы выдать доступ новому сотруднику, достаточно добавить его в профиль (`GRANT app_readonly TO new_user`). Не нужно перечислять все таблицы и схемы — права уже определены на уровне профиля.

### 4.1. `SET ROLE` — временное переключение

Пользователь может временно переключиться на роль, которая ему выдана:

```sql
-- Текущий контекст сеанса
SELECT current_user, session_user;
-- current_user:  analyst_ivanova   (активная роль)
-- session_user:  analyst_ivanova   (роль входа, не меняется)

-- Переключиться
SET ROLE app_readwrite;
-- current_user: app_readwrite

-- Вернуться к исходной роли
RESET ROLE;
```

> **Зачем это аналитику.** `SET ROLE` — безопасный способ проверить, что новая роль действительно видит только положенное. В лаб. 02 вы будете проверять RLS именно так: подключиться суперпользователем, `SET ROLE analyst_ivanova` и посмотреть, сколько строк вернёт `SELECT`.

### 4.2. `NOINHERIT` и явное включение роли

Если у роли `NOINHERIT`, привилегии выданных ей ролей не действуют автоматически. Их нужно включать командой `SET ROLE`. Это используют для «опасных» профилей: например, роль с правом `DELETE` не должна применяться случайно.

## 5. Аутентификация: цепочка от клиента до привилегий

Важно разделить два понятия:

- **Аутентификация** — «кто вы?» — управляется через `pg_hba.conf` и метод проверки пароля/сертификата.
- **Авторизация** — «что вам можно?» — управляется через `GRANT`/`REVOKE`, RLS и атрибуты роли.

```
Клиент
  │  1. Устанавливает TCP-соединение (host, port)
  ▼
postgresql.conf: listen_addresses, port
  │  2. Слушает ли сервер этот интерфейс?
  ▼
pg_hba.conf
  │  3. Проверяет: тип соединения, база, роль, IP-адрес → выбирает метод
  ▼
Механизм аутентификации
  │  4. Клиент подтверждает личность (пароль, OS-пользователь, сертификат)
  ▼
PostgreSQL Backend
  │  5. Проверяет атрибут LOGIN и ограничения роли
  ▼
Привилегии на объекты
  │  6. GRANT, RLS, ownership
  ▼
Таблица / схема / функция
```

**Типичные ошибки на разных шагах:**

| Сообщение                                         | На каком шаге сломалось                        | Кто исправляет         |
| ------------------------------------------------- | ---------------------------------------------- | ---------------------- |
| `could not connect to server: Connection refused` | Шаг 1–2: сервер не слушает или firewall        | DBA / DevOps           |
| `no pg_hba.conf entry for host ...`               | Шаг 3: нет подходящего правила                 | DBA                    |
| `password authentication failed`                  | Шаг 4: неверный пароль или несовместимый метод | DBA + пользователь     |
| `role "x" is not permitted to log in`             | Шаг 5: у роли нет `LOGIN`                      | DBA                    |
| `permission denied for table orders`              | Шаг 6: нет `SELECT`                            | DBA по матрице доступа |
| `permission denied for schema public`             | Шаг 6: нет `USAGE` на схему                    | DBA                    |

> **Частая ошибка:** роль создана в PostgreSQL, но правила в `pg_hba.conf` не добавлены. Клиент получает ошибку `pg_hba.conf rejects connection`, хотя роль существует. DBA управляет `pg_hba.conf`; задача аналитика — сообщить DBA, откуда будет подключаться роль (localhost, VPN, внутренняя подсеть).

### 5.1. Методы аутентификации

| Метод           | Суть                                                  | Применение                                       |
| --------------- | ----------------------------------------------------- | ------------------------------------------------ |
| `trust`         | Без проверки пароля                                   | Только локальная разработка, изолированная среда |
| `peer`          | ОС-пользователь совпадает с ролью БД (Unix-сокет)     | Локальные системные скрипты                      |
| `md5`           | Пароль в MD5-хеше                                     | Устаревший; небезопасен для production           |
| `scram-sha-256` | Современный протокол с взаимной аутентификацией       | Рекомендован с PostgreSQL 14+                    |
| `cert`          | Клиентский TLS-сертификат                             | High-security окружения                          |
| `ldap`          | Делегирование в корпоративный LDAP / Active Directory | Корпоративные среды                              |

> **SCRAM-SHA-256 — не «просто другой хеш».** Это challenge-response протокол: пароль не передаётся по сети даже в зашифрованном виде. Поэтому переход с `md5` на `scram-sha-256` требует, чтобы пароль роли был перезадан: старый MD5-хеш нельзя автоматически превратить в SCRAM.

### 5.2. Что сообщать DBA при запросе новой роли

```markdown
Роль/пользователь:        <имя>
Тип:                      LOGIN (персональный) / NOLOGIN (профиль-группа)
Откуда подключается:      localhost / 10.0.1.0/24 / через PgBouncer / VPN
Метод аутентификации:     scram-sha-256 (если нет спецтребований — этот)
Базы данных:              <список баз>
Объекты и привилегии:     см. матрицу доступа (лекция 4)
Срок действия:            бессрочно / до <дата>
Ответственный:            <ФИО, отдел>
```

## 6. Проектирование ролевой модели для продуктовой команды

### 6.1. Типовая трёхуровневая схема

```
postgres           (SUPERUSER) ──── только для DBA
  │
  ├── app_readonly (NOLOGIN) ──── профиль: только чтение
  │     ├── analyst_ivanova (LOGIN, VALID UNTIL '2027-01-01')
  │     └── analyst_petrov  (LOGIN)
  │
  ├── app_readwrite (NOLOGIN) ──── профиль: чтение + запись
  │     └── app_user (LOGIN, CONNECTION LIMIT 100)
  │
  └── migration_runner (LOGIN) ──── для CI/CD (Flyway migrate)
```

| Профиль            | Предназначен для                   | Типичные привилегии                        |
| ------------------ | ---------------------------------- | ------------------------------------------ |
| `app_readonly`     | Аналитики, BI-инструменты, репорты | `SELECT` на все таблицы схемы              |
| `app_readwrite`    | Приложение                         | `SELECT, INSERT, UPDATE, DELETE`           |
| `app_admin`        | Административные скрипты           | `app_readwrite` + `TRUNCATE`, объекты DDL  |
| `migration_runner` | CI/CD pipeline (Flyway)            | Расширенные права только на время миграции |

### 6.2. Принцип минимальных привилегий

Каждая роль получает **только те права, которые необходимы для выполнения задачи**:

- Аналитик → `SELECT` (только чтение).
- Приложение → `SELECT, INSERT, UPDATE, DELETE` (без `DROP`, `TRUNCATE`).
- CI/CD миграции → отдельная роль, активна только во время деплоя.
- `postgres` (superuser) → только для DBA и экстренных ситуаций.

> **Ошибка, которую делают аналитики:** запрашивать `SUPERUSER` «для удобства». Суперпользователь обходит все политики безопасности, включая RLS, — это недопустимо для учётных записей приложений и аналитиков.

### 6.3. Жизненный цикл роли

| Этап                 | Действие                                 | Ответственный           |
| -------------------- | ---------------------------------------- | ----------------------- |
| Запрос доступа       | Тикет с шаблоном требований              | Аналитик / руководитель |
| Создание             | `CREATE ROLE`, `GRANT profile`           | DBA                     |
| Согласование         | Проверка ИБ, особенно для ПДн            | ИБ                      |
| Эксплуатация         | Периодический аудит прав                 | DBA + ИБ                |
| Изменение            | `ALTER ROLE`, смена профиля              | DBA                     |
| Увольнение / перевод | `ALTER ROLE ... NOLOGIN`, отзыв профилей | DBA + HR                |

> **Правило «нет вечных паролей».** Для внешних подрядчиков и временных сотрудников ставьте `VALID UNTIL`. Для сервисных ролей — ротацию пароля и хранение в секрет-менеджере.

### 6.4. Шаблон требований к ролям (передаётся DBA)

```markdown
## Требования к ролям — [Имя проекта]

| Роль | Тип | Откуда | Базы | Метод аутентификации | Срок | Ответственный |
|---|---|---|---|---|---|---|
| app_user | LOGIN | 10.0.1.0/24 | myapp_prod | scram-sha-256 | бессрочно | Иванов А.П., backend |
| analyst_ivanova | LOGIN | VPN (10.0.2.0/24) | myapp_prod | scram-sha-256 | 2027-01-01 | Иванова М.С., аналитика |
| migration_runner | LOGIN | CI/CD (10.0.3.5) | myapp_prod | scram-sha-256 | бессрочно | DevOps |
| app_readonly | NOLOGIN | — | — | — | — | — (профиль) |
| app_readwrite | NOLOGIN | — | — | — | — | — (профиль) |
```

## 7. Разбор вводного кейса

1. **Какие требования не указаны?**  
   Откуда подключается аналитик (VPN-подсеть), срок действия, уровень доступа к персональным данным, запрет на передачу пароля в git, ответственный за блокировку при увольнении.
2. **Почему `SELECT` на таблицу — не «только смотреть заказы»?**  
   `SELECT` на `orders` даёт доступ ко всем строкам и всем колонкам. Нужны либо column-level привилегии, либо представление, либо RLS-политика (лекция 4). Без этого BI-аналитик видит данные всех клиентов.
3. **Кто отвечает за блокировку?**  
   Процесс должен быть формализован: HR сообщает DBA, DBA выполняет `ALTER ROLE ... NOLOGIN` и отзывает профили. Технически роль остаётся, но войти нельзя. Удаление — только после `REASSIGN OWNED`/`DROP OWNED`, если роль владеет объектами.

## Зачем это системному аналитику

Системный аналитик редко является администратором БД, но он обязан уметь поднять локальную среду — иначе невозможно проверить migration plan до отправки в review, воспроизвести баг в тестовой копии или написать runbook на основе реального поведения системы.

«Работает на моей машине» не работает, если машина у каждого настроена по-разному. Поэтому в команде фиксируются версия PostgreSQL, имя базы, способ запуска и набор параметров. Локальная среда — это не «игрушечная база», а полигон, на котором проверяются те же команды, что пойдут в production.

Понимание `pg_hba.conf` и конфигурационных файлов помогает аналитику самостоятельно разобраться, почему приложение не может подключиться к БД, — вместо того чтобы ждать DBA часами. Знание `psql` позволяет быстро проверить состояние схемы или права пользователя без GUI.

## 1. Вводный кейс

> **Кейс из практики.**  
> Аналитик подготовил migration plan, приложение на staging не запускается: `FATAL: password authentication failed for user "app_user"`.  
> Разработчик говорит: «Пароль правильный, я проверял». DBA занят.  
>  
> Через два часа выясняется:
> - роль `app_user` создана в кластере;
> - пароль задан;
> - но в `pg_hba.conf` для подсети staging стоит метод `md5`, а пароль хранится в формате `SCRAM-SHA-256`;
> - кроме того, в `postgresql.conf` `listen_addresses = 'localhost'`, поэтому приложение с другого хоста вообще не должно было достучаться.

**Вопросы аудитории:**
1. Какие два файла конфигурации участвуют в этой ошибке и за что отвечает каждый?
2. Почему «пароль правильный» не означает «подключение возможно»?
3. Что должен был проверить аналитик до передачи migration plan в staging?

К концу лекции мы разберём цепочку подключения по шагам и поймём, где именно она ломается.

## 2. Зачем аналитику локальная БД

Системный аналитик работает с БД не только в рамках чтения данных. Типичные задачи, которые требуют локального экземпляра:

- **Проверка migration plan** — запустить скрипт миграции на «чистой» БД перед отправкой MR.
- **Написание тестовых запросов** — не загружать production, не рисковать данными.
- **Разработка runbook** — воспроизвести сценарий восстановления в безопасной среде.
- **Изучение прав доступа** — безопасно экспериментировать с ролями и привилегиями.
- **Проверка ERD** — создать схему из миграций и убедиться, что кардинальности и ограничения совпадают с документацией.

Принцип: **каждый член команды, касающийся БД, должен иметь возможность поднять локальную копию за 10 минут.**

> **Важно.** Локальная база не должна содержать production-данные. Персональные данные (152-ФЗ, лекция 11) требуют либо анонимизации, либо синтетического набора. «Скачаю дамп прода, чтобы посмотреть» — типичная причина утечки.

## 3. Варианты установки PostgreSQL

| Способ | Когда использовать | Плюсы | Минусы |
|---|---|---|---|
| **EDB Installer** | Windows, первое знакомство | Графический мастер, включает pgAdmin | Сложнее управлять версиями |
| **apt / yum** | Linux (Ubuntu, Debian, RHEL, CentOS) | Интеграция с systemd, обновления через пакетный менеджер | Нужен доступ к репозиторию |
| **Homebrew** | macOS | `brew install postgresql@18` — просто | Только для разработки |
| **Docker** | Любая ОС; несколько версий одновременно; CI/CD | Изоляция, воспроизводимость, быстрый сброс | Требует Docker Desktop |
| **Managed (RDS, Cloud SQL, YDB)** | Production в облаке | Управляемый бэкап, HA из коробки | Нет прямого доступа к файловой системе |

### 3.1. Установка через EDB Installer (Windows / macOS)

1. Скачать с https://www.enterprisedb.com/downloads/postgres-postgresql-downloads
2. Запустить установщик → выбрать компоненты: PostgreSQL Server, Command Line Tools, pgAdmin (опционально).
3. Задать **пароль суперпользователя `postgres`** — запомнить!
4. Порт по умолчанию: `5432`.
5. После установки сервис `postgresql-x64-18` запускается автоматически.

**Что важно зафиксировать в README проекта:**

```
Версия: PostgreSQL 18.x
Порт: 5432
Сервис Windows: postgresql-x64-18
Каталог bin: C:\Program Files\PostgreSQL\18\bin
Каталог данных: C:\Program Files\PostgreSQL\18\data
```

### 3.2. Установка через Docker (рекомендуется для командной разработки)

Предпочтительный способ — `docker-compose.yml`, чтобы зафиксировать версию и параметры в git:

```yaml
# docker-compose.yml
services:
  postgres:
    image: postgres:18
    container_name: pg_local
    environment:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: mysecret
      POSTGRES_DB: dev
    ports:
      - "5432:5432"
    volumes:
      - pg_data:/var/lib/postgresql/data

volumes:
  pg_data:
```

```bash
# Запустить
docker compose up -d

# Подключиться через psql внутри контейнера
docker exec -it pg_local psql -U postgres -d dev

# Остановить (данные сохраняются в volume)
docker compose down

# Остановить И удалить данные (полный сброс)
docker compose down -v
```

Для разовых экспериментов без сохранения данных:

```bash
docker run --rm -d \
  --name pg_local \
  -e POSTGRES_PASSWORD=mysecret \
  -p 5432:5432 \
  postgres:18
```

> **Почему Docker удобен аналитику.** Можно держать рядом PostgreSQL 16, 17 и 18 и проверять, как миграция ведёт себя на разных версиях. На одной Windows-машине три EDB-установки конфликтуют за порт и службу.

## 4. Структура каталога PGDATA

`PGDATA` — корневой каталог данных кластера PostgreSQL. На Windows обычно `C:\Program Files\PostgreSQL\18\data`, на Linux — `/var/lib/postgresql/18/main`.

```
PGDATA/
├── base/               ← данные баз (одна папка на базу, имя = OID)
│   ├── 1/              ← template1
│   ├── 4/              ← postgres
│   └── 16384/          ← пользовательская БД
├── global/             ← объекты уровня кластера (роли, pg_database)
├── pg_wal/             ← файлы WAL (сегменты по 16 МБ)
├── log/                ← лог-файлы сервера (настраивается log_directory)
├── pg_tblspc/          ← симлинки на табличные пространства
├── postgresql.conf     ← основная конфигурация
├── pg_hba.conf         ← правила аутентификации клиентов
├── pg_ident.conf       ← маппинг системных пользователей на роли БД
├── postgresql.auto.conf ← параметры из ALTER SYSTEM; перекрывает postgresql.conf
├── postmaster.pid       ← PID главного процесса; отсутствует, когда сервер остановлен
└── PG_VERSION           ← мажорная версия кластера (например, «18»)
```

> **Важно.** Никогда не редактировать файлы в `base/` или `pg_wal/` вручную — это повреждает кластер. Конфигурационные файлы (`.conf`) редактировать можно.

### 4.1. Как читать `postmaster.pid`

Файл `postmaster.pid` появляется при старте сервера и исчезает при корректной остановке. Внутри — PID главного процесса и служебная информация.

- Файл есть, процесс жив → сервер работает.
- Файла нет → сервер остановлен.
- Файл есть, но процесса с таким PID нет → «осиротевший» файл после аварийного завершения. PostgreSQL при старте сам разберётся, но вручную удалять его без анализа причин опасно.

## 5. Конфигурационные файлы

### 5.1. `postgresql.conf` — основная конфигурация

Ключевые параметры, которые нужно понимать:

| Параметр | По умолчанию | Для локальной разработки | Назначение |
|---|---|---|---|
| `listen_addresses` | `localhost` | `localhost` | Сетевые интерфейсы для прослушивания (`*` — все) |
| `port` | `5432` | `5432` | Порт TCP |
| `max_connections` | `100` | `20–50` | Максимум параллельных соединений к кластеру |
| `shared_buffers` | `128MB` | `256MB` | Кэш страниц в оперативной памяти |
| `work_mem` | `4MB` | `16–64MB` | Память на одну операцию сортировки / хеш-соединения |
| `maintenance_work_mem` | `64MB` | `256MB` | Память для VACUUM, CREATE INDEX |
| `wal_level` | `replica` | `replica` | Уровень детализации WAL |
| `log_destination` | `stderr` | `stderr` | Куда писать логи |
| `logging_collector` | `off` | `on` | Включить сбор логов в файлы |
| `log_directory` | `log` | `log` | Папка для лог-файлов (относительно PGDATA) |
| `log_statement` | `none` | `all` | Какие SQL-операторы логировать |
| `log_min_duration_statement` | `-1` | `100` | Логировать запросы дольше N мс (`-1` — отключено) |
| `effective_cache_size` | `4GB` | `512MB` | Подсказка планировщику об объёме кэша ОС; влияет на выбор плана |

Применить изменения без перезапуска (для большинства параметров):

```sql
SELECT pg_reload_conf();
```

> **Важно:** параметры `shared_buffers` и `max_connections` требуют **полного перезапуска** сервера — `pg_reload_conf()` для них не работает. Список параметров, требующих перезапуска:
> ```sql
> SELECT name, context FROM pg_settings WHERE context = 'postmaster' ORDER BY name;
> ```

Проверить текущее значение параметра:

```sql
SHOW shared_buffers;
SHOW log_statement;

-- Откуда взято значение: файл, ALTER SYSTEM, командная строка?
SELECT name, setting, source, sourcefile, sourceline
FROM   pg_settings
WHERE  name IN ('shared_buffers', 'work_mem');
```

> **`postgresql.auto.conf` перекрывает `postgresql.conf`.** Если DBA выполнил `ALTER SYSTEM SET work_mem = '32MB'`, то правка `work_mem` в `postgresql.conf` не даст эффекта. Всегда проверяйте столбец `source` в `pg_settings`.

### 5.2. `pg_hba.conf` — правила аутентификации

Файл читается сверху вниз; применяется первое совпавшее правило.

```
# Тип   База    Пользователь  Адрес            Метод
local   all     postgres                       peer
local   all     all                            scram-sha-256
host    all     all           127.0.0.1/32     scram-sha-256
host    all     all           ::1/128          scram-sha-256
```

| Тип | Когда используется |
|---|---|
| `local` | Подключение через Unix-сокет (только Linux/macOS) |
| `host` | Подключение по TCP/IP (в т.ч. localhost через сеть) |
| `hostssl` | TCP только с TLS (лекция 11) |
| `hostnossl` | TCP только без TLS (не рекомендуется) |

| Метод | Суть |
|---|---|
| `trust` | Без пароля — только для локальной разработки в изолированной среде |
| `peer` | ОС-пользователь совпадает с ролью БД (только Unix-сокет) |
| `md5` | Пароль в MD5 (устаревший, небезопасен для production) |
| `scram-sha-256` | Современный стандарт; рекомендован с PostgreSQL 14+ |
| `cert` | Клиентский TLS-сертификат |

После изменения `pg_hba.conf` нужно перезагрузить конфигурацию:

```sql
SELECT pg_reload_conf();
```

```bash
pg_ctl reload -D /путь/к/PGDATA
```

> **Порядок правил имеет значение.** Строка `host all all 0.0.0.0/0 trust`, добавленная выше остальных, откроет базу всему миру без пароля. Проверка «первое совпадение» — не формальность, а механизм безопасности.

### 5.3. Три файла, которые путают

| Файл | На какой вопрос отвечает | Кто меняет |
|---|---|---|
| `postgresql.conf` | «Как работает сервер?» (память, порт, логи) | DBA |
| `pg_hba.conf` | «Кому и как можно подключаться?» | DBA |
| `pg_ident.conf` | «Как системный пользователь ОС превращается в роль БД?» (для `peer`/`cert`) | DBA |

Аналитик должен уметь прочитать первые два и точно сформулировать, что именно нужно изменить.

## 6. Управление сервером

### 6.1. `pg_ctl` — утилита управления

```bash
# Запустить сервер
pg_ctl start -D /path/to/PGDATA

# Остановить — три режима:
# smart    — ждёт завершения всех соединений (аккуратно, но долго)
# fast     — прерывает соединения, делает checkpoint (обычный выбор)
# immediate — аварийная остановка без checkpoint; при следующем старте потребуется recovery из WAL
pg_ctl stop -D /path/to/PGDATA -m fast

# Перезапустить
pg_ctl restart -D /path/to/PGDATA

# Проверить статус
pg_ctl status -D /path/to/PGDATA

# Перечитать конфигурацию (без перезапуска)
pg_ctl reload -D /path/to/PGDATA
```

**Три режима остановки — не взаимозаменяемы:**

| Режим | Что делает | Когда применять |
|---|---|---|
| `smart` | Ждёт отключения клиентов | Плановое обслуживание без срочности |
| `fast` | Откатывает активные транзакции, checkpoint, остановка | Стандартная остановка |
| `immediate` | Аварийная остановка без checkpoint | Только когда сервер завис; при старте будет recovery |

### 6.2. `systemctl` (Linux)

```bash
sudo systemctl start postgresql
sudo systemctl stop postgresql
sudo systemctl restart postgresql
sudo systemctl status postgresql
sudo systemctl enable postgresql   # автозапуск при старте ОС
```

### 6.3. Windows — `pg_ctl` через PowerShell

```powershell
$pg = "C:\Program Files\PostgreSQL\18\bin"
$data = "C:\Program Files\PostgreSQL\18\data"

# Статус
& "$pg\pg_ctl.exe" status -D $data

# Запустить / остановить / перезапустить
& "$pg\pg_ctl.exe" start   -D $data
& "$pg\pg_ctl.exe" stop    -D $data -m fast
& "$pg\pg_ctl.exe" restart -D $data

# Перечитать конфигурацию без перезапуска
& "$pg\pg_ctl.exe" reload  -D $data
```

Или через Службы: `services.msc` → `postgresql-x64-18` → Запустить / Остановить. В PowerShell от администратора:

```powershell
Get-Service postgresql-x64-18
Restart-Service postgresql-x64-18
```

**Упражнение.** Вы изменили `work_mem` в `postgresql.conf` и запустили `pg_reload_conf()`. Изменился ли параметр?

<details><summary>Ответ</summary>

`work_mem` имеет контекст `user`, а не `postmaster` — значит, он применяется без перезапуска через `pg_reload_conf()`. Проверить:

```sql
SHOW work_mem;
SELECT name, context, source FROM pg_settings WHERE name = 'work_mem';
```

Если в `source` указан `configuration file`, значение пришло из `postgresql.conf`; если `override` — из `ALTER SYSTEM`; если `session` — из `SET`.

</details>

## 7. Установка и настройка DBeaver

DBeaver — GUI-клиент для работы с PostgreSQL. Выполняет роль инструмента на стороне клиента.

> Подробнее о типичных ловушках DBeaver — в статье [DBeaver](../../wiki/tools/dbeaver.md).

### 7.1. Установка

Скачать Community-версию: https://dbeaver.io/download/  
Требования: Java 17+ (DBeaver включает JRE).

### 7.2. Создание подключения

1. **Database → New Database Connection → PostgreSQL**
2. Заполнить:
   - Host: `localhost`
   - Port: `5432`
   - Database: `postgres`
   - Username: `postgres`
   - Password: ваш пароль
3. Нажать **Test Connection** — при первом запуске DBeaver предложит скачать JDBC-драйвер.

### 7.3. Обязательная настройка — Local Client

DBeaver использует внешние утилиты `pg_dump` и `pg_restore` для резервного копирования. Без этой настройки кнопки **Dump / Restore** не работают.

Настройки подключения → вкладка **Local Client** → указать путь к папке `bin` установленного PostgreSQL:
- Windows: `C:\Program Files\PostgreSQL\18\bin`
- Linux: `/usr/lib/postgresql/18/bin` (универсальный способ: `which pg_dump | xargs dirname`)

> **Признак ошибки.** Если DBeaver предлагает «скачать драйвер» для `pg_dump` или жалуется на версию клиента — почти всегда не указан Local Client.

### 7.4. Полезные возможности DBeaver

| Функция | Где найти |
|---|---|
| SQL-редактор | SQL Editor → Open SQL Script (Alt+F3) |
| ERD-диаграмма | ПКМ по схеме → View Diagram |
| Экспорт данных | ПКМ по таблице → Export Data |
| Dump базы | ПКМ по БД → Tools → Dump Database |
| Restore базы | ПКМ по БД → Tools → Restore Database |
| EXPLAIN ANALYZE | Открыть план запроса: Ctrl+Shift+E (но `Execution Time` и `Buffers` показывает только `EXPLAIN (ANALYZE, BUFFERS)` через Ctrl+Enter) |

> **Ловушка DBeaver.** В режиме ручных транзакций `VACUUM`, `CREATE INDEX CONCURRENTLY` и `CREATE DATABASE` не выполняются: они не могут работать внутри блока транзакции. Для таких команд включайте Auto-Commit (подробно — в лаб. 07).

## 8. `psql` — командная строка

`psql` — основной CLI-клиент PostgreSQL; поставляется вместе с сервером.

> Полный справочник метакоманд и сценариев автоматизации — в статье [psql](../../wiki/tools/psql.md).

### 8.1. Подключение

```bash
# Подключиться к базе postgres пользователем postgres
psql -h localhost -p 5432 -U postgres -d postgres

# Подключиться к конкретной базе
psql -h localhost -U postgres -d mydb

# Рекомендованный способ — файл ~/.pgpass (host:port:database:user:password):
#   localhost:5432:*:postgres:mysecret
# Установить права (обязательно, иначе psql игнорирует файл):
#   chmod 600 ~/.pgpass
psql -h localhost -U postgres

# PGPASSWORD=... — не использовать: пароль попадает в историю shell и в ps aux
```

### 8.2. Мета-команды `psql`

| Команда | Действие |
|---|---|
| `\l` | Список баз данных кластера |
| `\c dbname` | Переключиться на базу `dbname` |
| `\dn` | Список схем в текущей базе |
| `\dt` | Список таблиц в текущей схеме |
| `\dt *.*` | Список таблиц во всех схемах |
| `\d tablename` | Структура таблицы (колонки, индексы, FK) |
| `\du` | Список ролей (пользователей) |
| `\dp tablename` | Привилегии на таблицу |
| `\timing` | Показывать время выполнения запросов |
| `\i file.sql` | Выполнить SQL-скрипт из файла |
| `\e` | Открыть текущий запрос во внешнем редакторе |
| `\x` | Переключить расширенный вывод (удобно для широких строк) |
| `\conninfo` | Показать параметры текущего подключения |
| `\h SELECT` | Справка по синтаксису SQL-команды |
| `\q` | Выйти из psql |

### 8.3. Выполнение SQL-скрипта из файла

```bash
# Выполнить скрипт из командной строки
psql -h localhost -U postgres -d mydb -f migration.sql

# Внутри psql
\i /path/to/migration.sql
```

> **PowerShell.** Не направляйте вывод утилит PostgreSQL в файл через `>`. Windows PowerShell 5.1 пишет в UTF-16, и `psql -f` / `pg_restore -L` не смогут прочитать файл. Используйте штатный флаг `-f` или `-o`.

## 9. Конвенции локальной среды разработчика

Чтобы работа с локальной БД была предсказуемой в команде, договоритесь о следующем:

| Параметр | Рекомендация |
|---|---|
| Версия PostgreSQL | Совпадает с production; фиксируется в `docker-compose.yml` или README |
| Имя базы | Имя приложения одинаковое, суффикс различается: `myapp_dev` / `myapp_test` / `myapp` (prod) |
| Пользователь | Отдельная роль приложения (не `postgres`) |
| Данные | Только тестовые / анонимизированные — никогда prod-данные |
| Миграции | Применяются через Flyway: `flyway migrate` |
| Сброс среды | `flyway clean && flyway migrate` — **только для dev!** `clean` уничтожает все объекты схемы без подтверждения. На staging/prod обязательно `flyway.cleanDisabled=true` |

> **Правило «трёх одинаковых».** Локальная среда, staging и production должны совпадать по мажорной версии PostgreSQL, набору расширений и порядку применения миграций. Всё остальное (объём данных, мощность железа) может отличаться.

> **Практика →** [Лаб. 01 — установка PostgreSQL, настройка `postgresql.conf` и подключение через DBeaver/psql](../../labs/lab_01/lab_01.md).

## 10. Разбор вводного кейса

1. **Какие два файла конфигурации участвуют?**  
   `postgresql.conf` (`listen_addresses`) отвечает за то, на каких интерфейсах сервер слушает подключения. `pg_hba.conf` (`host ... md5`) — за метод аутентификации для конкретной подсети.
2. **Почему «пароль правильный» не означает «подключение возможно»?**  
   Подключение проходит несколько независимых проверок: сеть (`listen_addresses`, firewall) → правило `pg_hba.conf` → метод аутентификации → атрибут роли `LOGIN` → привилегии на базу. Ошибка на любом шаге даёт отказ, даже если пароль верный.
3. **Что должен был проверить аналитик?**  
   В требованиях к среде указать: откуда подключается приложение (подсеть), каким методом аутентификации, под какой ролью, к какой базе. Это данные для DBA, без которых `pg_hba.conf` не настроить.

## 11. Итоги лекции

После этой лекции студент умеет:

- **Установить PostgreSQL** через EDB Installer или Docker и убедиться, что сервер запущен (`pg_ctl status`, `systemctl status`, `Get-Service`).
- **Найти и изменить** ключевые параметры в `postgresql.conf` (`shared_buffers`, `work_mem`, `log_*`) и применить через `pg_reload_conf()` или перезапуск.
- **Объяснить разницу** между `postgresql.conf` и `pg_hba.conf`: параметры сервера vs правила аутентификации.
- **Использовать psql**: подключаться, выполнять метакоманды (`\dt`, `\d`, `\l`, `\c`), запускать SQL-файл через `\i`.
- **Подключить DBeaver** к локальному PostgreSQL, настроить Local Client для Dump/Restore.
- **Обосновать** принцип: версия PostgreSQL в локальной среде должна совпадать с production.

## Зачем это системному аналитику

Информационная безопасность часто воспринимается как «зона ИБ и DBA». Но аналитик:

- классифицирует данные в требованиях (где персональные данные, где нет);
- определяет, кто и зачем получает доступ;
- описывает, какие действия должны аудироваться;
- проверяет, что миграция не расширяет права и не создаёт новую таблицу с ПДн без защиты.

Ошибка в требованиях к ИБ стоит дороже, чем ошибка в производительности: штраф по 152-ФЗ, утечка данных клиентов, репутационный ущерб. При этом исправлять её постфактум почти невозможно — данные уже собраны и разложены по таблицам.

> **Ключевая мысль.** Безопасность БД — это не «включить TLS». Это набор слоёв: сеть, аутентификация, авторизация, аудит, шифрование, регламенты. Каждый слой закрывает свой класс угроз.

## 1. Вводный кейс

> **Кейс из практики.**  
> В `eshop` решили «усилить безопасность»: включили `log_statement = all`, чтобы «видеть все запросы».  
> Через месяц:
> - лог-файлы выросли до сотен гигабайт;
> - в логах оказались пароли, которые приложение передавало в `CREATE ROLE ... PASSWORD '...'`;
> - подрядчик, имеющий доступ к серверу, прочитал логи и получил эти пароли;
> - при разборе инцидента выяснилось, что удаление таблицы `customers` никем не зафиксировано, потому что `pgaudit` не был установлен;
> - TLS был выключен: приложение подключалось по открытому TCP внутри сети.

## 2. Угрозы информационной безопасности для БД

### 2.1. Модель угроз

| Угроза | Пример | Меры защиты |
|---|---|---|
| **SQL-инъекция** | `' OR 1=1 --` в поле ввода | Параметризованные запросы; `GRANT` только нужных операций |
| **Избыточные привилегии** | Приложение работает под `postgres` (superuser) | Принцип минимальных привилегий; отдельная роль |
| **Утечка через лог-файлы** | Пароль или PAN в тексте SQL попал в лог | `log_statement = none` для prod; маскирование; аудит вместо полного лога |
| **Несанкционированный доступ** | Бывший сотрудник подключается с личного ноутбука | Немедленный отзыв (`NOLOGIN`); IP-ограничения в `pg_hba.conf` |
| **Атака через незащищённый порт** | PostgreSQL слушает `0.0.0.0:5432` без пароля | `listen_addresses = 'localhost'`; firewall |
| **Дамп данных через ФС** | Прямой доступ к `PGDATA` | Шифрование диска; ограничение ОС-доступа |
| **Insider threat** | DBA намеренно или случайно удаляет данные | Аудит (`pgAudit`); разделение обязанностей |
| **Подмена `search_path`** | Злоумышленник создаёт объект в схеме раньше доверенной | Фиксация `search_path` на уровне роли |
| **Кража резервной копии** | Дамп с ПДн лежит в открытом S3-бакете | Шифрование бэкапов; ограничение доступа |

> Подробнее о модели угроз и слоях защиты — в статье [Безопасность](../../wiki/concepts/security.md).

### 2.2. Минимальный чек-лист безопасности БД

```markdown
[ ] Роль приложения — не postgres (не superuser)
[ ] pg_hba.conf: нет trust для non-local соединений
[ ] Пароли: scram-sha-256 (не md5)
[ ] Неиспользуемые роли: NOLOGIN или удалены
[ ] Порт PostgreSQL закрыт на уровне firewall для внешнего мира
[ ] Логирование включено; лог-файлы не содержат паролей
[ ] Дамп-файлы с ограниченным доступом, зашифрованы
[ ] SSL/TLS: включён (ssl = on)
[ ] Аудит: pgAudit установлен и настроен для DDL и привилегированных операций
[ ] RLS: включён на таблицах с персональными данными
```

> Полный чек-лист для сдачи — в статье [ИБ-чек-лист](../../wiki/artifacts/security-checklist.md).

## 3. 152-ФЗ и персональные данные в БД

Федеральный закон № 152-ФЗ «О персональных данных» регулирует обработку персональных данных граждан РФ.

### 3.1. Категории персональных данных

| Категория | Примеры | Уровень защиты |
|---|---|---|
| **Специальные** (ч. 1 ст. 10) | Здоровье, биометрия, национальность | Максимальный |
| **Общие** | ФИО, дата рождения, адрес, телефон, email | Стандартный |
| **Общедоступные** | Опубликованные самим субъектом | Минимальный |

> **Как это выглядит в `eshop`.** Таблица `customers` содержит ФИО, email, телефон, регион — общие персональные данные. Если добавить `passport_data` или медицинские отметки, категория меняется и требования ужесточаются.

### 3.2. Требования к БД по 152-ФЗ

| Требование | Как реализовать в PostgreSQL |
|---|---|
| Разграничение доступа | RBAC + RLS |
| Журналирование доступа к ПДн | `pgAudit` (аудит `SELECT` на таблицы с ПДн) |
| Локализация данных граждан РФ | Инфраструктурное требование (серверы в РФ) |
| Уничтожение данных по запросу субъекта | `DELETE` или обфускация + запись в audit-лог |
| Шифрование при хранении | Шифрование диска (ОС) или `pgcrypto` |
| Шифрование при передаче | TLS (`ssl = on`) |

> **Важно.** 152-ФЗ — не технический стандарт. Он не говорит «включите `ssl=on`». Он требует обеспечить конфиденциальность и защиту от неправомерного доступа. DBA переводит эти требования в конкретные настройки, аналитик фиксирует их в требованиях и проверяет выполнение.

### 3.3. Задача аналитика при работе с ПДн

1. **Идентифицировать** таблицы и колонки с ПДн.
2. **Описать роли**, имеющие доступ к этим данным.
3. **Передать DBA** требования к RLS и аудиту.
4. **Убедиться**, что дамп-файлы с ПДн не хранятся без шифрования.
5. **Зафиксировать** срок хранения и сценарий уничтожения.
6. **Проверить**, что тестовые данные анонимизированы (или синтетические).

> **Типичная ошибка.** В requirements написано «данные клиентов», и разработчик создаёт одну таблицу `customers` с ФИО, телефоном и паспортом. Аналитик должен явно разделить: какие поля относятся к ПДн, какие — к бизнес-данным, и какие требуют особого режима.

## 4. `pgAudit`: аудит SQL-операций

`pgAudit` — расширение PostgreSQL для структурированного аудита SQL-операций. Записывает события в стандартный лог.

> Подробный справочник по установке, категориям и объектному аудиту — в статье [pgAudit](../../wiki/tools/pgaudit.md).

### 4.1. Зачем отдельный аудит, если есть лог

| Обычный лог | `pgAudit` |
|---|---|
| Пишет текст запроса или ничего | Структурированные записи: класс события, объект, команда |
| `log_statement = all` пишет всё, включая пароли | Можно аудировать только `ddl`, `role`, `write` |
| Трудно разобрать автоматически | Формат пригоден для SIEM и разбора |
| Нет разделения по объектам | Объектный аудит на уровне роли |

### 4.2. Установка

```ini
# postgresql.conf (требует перезапуска)
shared_preload_libraries = 'pgaudit'
```

> Важно: если `pg_stat_statements` уже подключён, добавляйте через запятую:
> ```ini
> shared_preload_libraries = 'pg_stat_statements,pgaudit'
> ```

```sql
CREATE EXTENSION pgaudit;
```

### 4.3. Session audit (уровень кластера)

```ini
# postgresql.conf
pgaudit.log          = 'ddl,role,misc_set'
# Категории: read, write, function, role, ddl, misc, misc_set, all

pgaudit.log_relation = on   # выводить имя объекта (таблица, индекс)
pgaudit.log_parameter = on  # логировать значения параметров запроса
```

> **Осторожно с `log_parameter`.** Значения параметров могут содержать персональные данные. Включайте только там, где это необходимо для расследования, и защищайте лог.

### 4.4. Object audit (уровень роли)

```sql
-- Аудировать все SELECT роли analyst_ivanova
ALTER ROLE analyst_ivanova SET pgaudit.log = 'read';

-- Аудит через специальную роль-монитор
GRANT SELECT ON users TO pgaudit_monitor;
ALTER ROLE pgaudit_monitor SET pgaudit.log = 'read';
```

### 4.5. Пример записи аудита

```
2024-09-01 16:22:33 MSK [12345]: LOG:  AUDIT: SESSION,1,1,DDL,DROP TABLE,TABLE,
  public.orders,"DROP TABLE orders",<not logged>
```

Поля: тип аудита, класс события, тип объекта, имя объекта, текст команды.

> **Как читать.** `SESSION` — сессионный аудит; `DDL` — класс; `DROP TABLE` — команда; `public.orders` — объект. Для объектного аудита первое поле будет `OBJECT`.

### 4.6. Что аудировать в первую очередь

| Категория | Что покрывает | Приоритет |
|---|---|---|
| `ddl` | `CREATE`, `ALTER`, `DROP` | Обязательно |
| `role` | `CREATE ROLE`, `GRANT`, `REVOKE` | Обязательно |
| `write` | `INSERT`, `UPDATE`, `DELETE`, `TRUNCATE` | Для таблиц с ПДн и финансовых |
| `read` | `SELECT` | Для таблиц с ПДн (может быть объёмным) |
| `function` | вызовы функций | По необходимости |
| `misc_set` | `SET`, `RESET` | Для расследования инцидентов |

> **Практика →** [Лаб. 08, часть 1 — установка `pgAudit` и проверка записи AUDIT](../../labs/lab_08/lab_08.md).

## 5. TLS и шифрование

### 5.1. TLS-шифрование соединений

```ini
# postgresql.conf
ssl            = on
ssl_cert_file  = 'server.crt'
ssl_key_file   = 'server.key'
ssl_ca_file    = 'root.crt'
```

```
# pg_hba.conf — требовать TLS для всех внешних соединений
hostssl  all  all  0.0.0.0/0  scram-sha-256
```

```sql
-- Проверить, что соединение использует TLS
SELECT pid, usename, ssl, version, cipher FROM pg_stat_ssl;
```

> **`hostssl` vs `host`.** `host` разрешает и TLS, и обычное соединение. `hostssl` требует TLS. Если в `pg_hba.conf` остался `host ... trust`, TLS можно обойти. Поэтому для внешних подключений используют `hostssl` и явно запрещают остальное.

### 5.2. Шифрование данных в колонках (`pgcrypto`)

```sql
CREATE EXTENSION pgcrypto;

-- Зашифровать
UPDATE users
SET    passport_data = pgp_sym_encrypt(passport_data, 'encryption_key');

-- Расшифровать
SELECT pgp_sym_decrypt(passport_data::bytea, 'encryption_key')
FROM   users WHERE id = 1;
```

> **Ключ — не в базе.** Если ключ хранится в той же базе или в коде приложения, шифрование защищает только от кражи файла БД, но не от компрометации приложения. В production ключи хранят в KMS/Vault и передают через защищённый канал.

### 5.3. Три уровня шифрования

| Уровень | Что защищает | Инструмент |
|---|---|---|
| **Канал** | Перехват трафика | TLS (`ssl = on`, `hostssl`) |
| **Диск** | Кража диска / файла `PGDATA` | BitLocker, LUKS, шифрование облачного тома |
| **Колонка** | Компрометация БД или бэкапа | `pgcrypto`, приложение |

> **Что выбрать.** Для большинства случаев достаточно TLS + шифрование диска. Колоночное шифрование нужно, когда требуется защита от DBA/облачного провайдера или выборочное шифрование особо чувствительных полей. Оно усложняет поиск и индексацию: зашифрованные данные нельзя сравнивать обычными операторами.

## 6. Регламент ИБ жизненного цикла БД

Аналитик участвует в разработке регламентов на каждом этапе:

| Этап | Задача ИБ | Роль аналитика |
|---|---|---|
| Проектирование схемы | Классификация данных; определение RLS-политик | Идентифицировать ПДн; описать матрицу доступа |
| Разработка и миграции | Контроль доступа к `migration_runner`; review SQL-скриптов | Убедиться, что миграция не расширяет привилегии без необходимости |
| Деплой | Не передавать пароли в CI/CD в открытом виде | Проверить secrets management (Vault, k8s secrets) |
| Эксплуатация | Мониторинг `pgAudit`; ротация паролей; аудит привилегий | Согласовывать запросы на новый доступ |
| Инцидент | Не удалять логи; не перезапускать без согласования ИБ | Эскалация по схеме из лекции 1 |
| Вывод из эксплуатации | Безопасное уничтожение данных; подтверждение в audit-логе | Составить чек-лист уничтожения данных |

### 6.1. Что делать при инциденте ИБ

1. **Не пытаться исправить самостоятельно.**
2. Зафиксировать время, пользователя, действие.
3. Передать в **службу ИБ** и **DBA одновременно**.
4. Сохранить логи и снимки состояния.
5. Не сообщать публично до завершения расследования.

> **Почему нельзя «просто удалить подозрительную сессию».** Это может уничтожить следы: транзакция откатится, временные объекты исчезнут, логи останутся неполными. Сначала — фиксация, потом — реакция.

## 7. Разбор вводного кейса

1. **Почему `log_statement = all` — не аудит?**  
   Он пишет всё подряд, включая пароли и персональные данные, не структурирует события и не позволяет выборочно аудировать объекты. Это источник утечек и лишней нагрузки.
2. **Чем `pgAudit` отличается?**  
   Категориями (`ddl`, `role`, `write`, `read`), структурированным форматом, объектным аудитом на уровне роли и возможностью не логировать параметры.
3. **Какие три слоя отсутствовали?**  
   Аудит (`pgAudit`), шифрование канала (TLS), и управление доступом к логам/бэкапам (ограничение доступа и шифрование).

## 8. Итоги лекции

После этой лекции студент умеет:

- **Настроить `pgAudit`**: `shared_preload_libraries`, категории `log = 'write, ddl, role'`, найти строку `AUDIT` в логе.
- **Принудить TLS**: `ssl=on`, добавить `hostssl` в `pg_hba.conf`, проверить через `pg_stat_ssl`.
- **Зашифровать чувствительные данные** через `pgcrypto`: `pgp_sym_encrypt` / `pgp_sym_decrypt`.
- **Определить категорию ПДн** по 152-ФЗ для конкретного набора данных и назвать основные меры защиты.
- **Составить ИБ-чек-лист** для производственной БД: аутентификация, сеть, аудит, шифрование, 152-ФЗ.

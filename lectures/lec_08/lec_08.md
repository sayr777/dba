**Неделя:** 8  
**Версия PostgreSQL:** 18  
**Практика:** лабораторная работа №6  
**Данные в примерах:** база `eshop` после наполнения в лаб. 06 — 20 000 клиентов, 1 000 товаров, 200 000 заказов, 600 000 позиций

---

## Цель лекции

По итогам лекции студент:

- находит самые дорогие запросы через `pg_stat_statements` и узнаёт проблему N+1;
- читает план `EXPLAIN ANALYZE` и отвечает на 4 вопроса: где время, верна ли оценка, сколько строк выброшено, сколько циклов;
- отличает случай, когда индекс поможет, от случая, когда не поможет;
- пишет измеримые требования к производительности: объём данных, рост, перцентили;
- передаёт DBA запрос, план и контекст одним документом и проверяет, выполнимо ли само требование.

## Зачем это системному аналитику

Аналитик не настраивает сервер — это работа DBA. Но многие медленные запросы появляются из требований и проектирования:
«выгрузить все заказы», «показать позиции каждого заказа в списке», «поиск без учёта регистра».
Аналитик первым получает жалобу «система тормозит» и должен превратить её в факт с числами.

## Порядок анализа

1. **Найти** дорогой запрос — `pg_stat_statements` (или pgBadger по журналу).
2. **Объяснить**, почему он дорогой, — `EXPLAIN (ANALYZE, BUFFERS)`.
3. **Исправить** — индекс, другой запрос, другое требование.
4. **Проверить** — повторный `EXPLAIN ANALYZE` и `pg_stat_statements` после сброса.

## 2. Найти: pg_stat_statements

`pg_stat_statements` — расширение PostgreSQL. Оно накапливает статистику по **всем** выполненным запросам:
сколько раз выполнен, сколько времени занял, сколько страниц прочитал.

Запросы группируются по структуре: константы заменяются параметрами.
`WHERE status = 'pending'` и `WHERE status = 'shipped'` попадают в одну строку `WHERE status = $1`.

> Подключение расширения — справочник, С.1, и лаб. 06, п. 1.1.

### 2.1. Топ-10 запросов

```sql
SELECT LEFT(regexp_replace(query, '\s+', ' ', 'g'), 80) AS query_preview,
       calls,
       ROUND(total_exec_time::numeric, 0) AS total_ms,
       ROUND(mean_exec_time::numeric, 1)  AS avg_ms,
       rows,
       shared_blks_hit + shared_blks_read AS pages
FROM   pg_stat_statements
WHERE  dbid = (SELECT oid FROM pg_database WHERE datname = current_database())
  AND  query NOT ILIKE '%pg_catalog%'
  AND  query NOT ILIKE '%pg_stat%'
ORDER  BY total_exec_time DESC
LIMIT  10;
```

**Три сортировки — три разных вопроса:**

| Сортировка        | Вопрос                                            | Кого находит                           |
| ----------------- | ------------------------------------------------- | -------------------------------------- |
| `total_exec_time` | Что сильнее всего нагружает сервер?               | Часто быстрые, но очень частые запросы |
| `mean_exec_time`  | Что медленнее всего для пользователя за один раз? | Тяжёлые отчёты                         |
| `calls`           | Что вызывается подозрительно часто?               | Проблему N+1 (п. 2.2)                  |

**Страниц на вызов** = `pages / calls`. Если значение близко к размеру таблицы в страницах
(`pg_relation_size('orders') / 8192`), запрос читает таблицу целиком. В лаб. 06 для запроса Q2 это 1 788 страниц — вся таблица `orders`.

### 2.2. Проблема N+1

Экран показывает 100 заказов клиента и позиции каждого заказа. Приложение (часто ORM) выполняет
1 запрос за списком заказов и затем **по одному запросу на каждый заказ** за позициями — всего 1 + 100 запросов.

Как это выглядит в `pg_stat_statements` (иллюстративные числа за сутки):

| query_preview                                                                   | calls   | avg_ms | total_ms |
| ------------------------------------------------------------------------------- | ------- | ------ | -------- |
| `SELECT … FROM orders WHERE customer_id = $1 ORDER BY created_at DESC LIMIT $2` | 1 200   | 0,4    | 480      |
| `SELECT … FROM order_items WHERE order_id = $1`                                 | 120 000 | 0,05   | 6 000    |

Признаки:

- каждый вызов быстрый (0,05 мс), в топе по `mean_exec_time` запроса нет;
- `calls` второго запроса ровно в 100 раз больше `calls` первого — по запросу на каждую строку списка;
- в топе по `total_exec_time` запрос есть.

Пользователь ждёт дольше, чем видно в статистике: каждый из 100 запросов — это ещё и отдельный обмен по сети между приложением и сервером.
`pg_stat_statements` считает только время на сервере.

**Решение** — получить позиции всех заказов одним запросом:

```sql
SELECT order_id, product_id, quantity, unit_price
FROM   order_items
WHERE  order_id = ANY($1);   -- $1 — массив из 100 номеров заказов
```

Было 1 + 100 запросов на экран, стало 2.

> **Для аналитика.** Требование «показать в списке заказов позиции каждого заказа» — источник N+1.
> Опишите в требованиях, что список строится ограниченным числом запросов, или договоритесь с разработчиками о способе загрузки.

### 2.3. Сброс статистики

```sql
SELECT pg_stat_statements_reset();
```

Сбрасывайте статистику до и после изменения (например, создания индекса). Иначе старые медленные вызовы смешаются с новыми.

### Упражнение 1. Что оптимизировать первым?

Эталонный прогон лаб. 06 (9 вызовов каждого запроса) и строка N+1 из п. 2.2:

| Запрос                  | calls   | avg_ms | total_ms |
| ----------------------- | ------- | ------ | -------- |
| Q3: продажи по товарам  | 9       | 651,5  | 5 864    |
| Q1: выручка по клиентам | 9       | 388,7  | 3 498    |
| Q2: заказы pending      | 9       | 68,4   | 616      |
| N+1: позиции заказа     | 120 000 | 0,05   | 6 000    |

Какой запрос оптимизировать первым? Ответ зависит от цели — сформулируйте её.

<details>
<summary>Ответ</summary>

- Цель «снизить нагрузку на сервер» — сортировка по `total_ms`: первым N+1 (6 000 мс), почти рядом Q3 (5 864 мс).
- Цель «пользователь ждёт меньше» — сортировка по `avg_ms`: первым Q3 (0,65 с на одно выполнение).
- N+1 к тому же добавляет сетевые задержки, которых в статистике нет.

Вывод: перед анализом договоритесь о цели. «Самый медленный запрос» — это неполная постановка.

</details>

## 3. Объяснить: EXPLAIN ANALYZE

`pg_stat_statements` говорит, **какой** запрос дорогой. `EXPLAIN` объясняет, **почему**.

| Вариант           | Что делает                                                                                       |
| ----------------- | ------------------------------------------------------------------------------------------------ |
| `EXPLAIN`         | Показывает план и **оценки** планировщика. Запрос не выполняется                                 |
| `EXPLAIN ANALYZE` | **Выполняет** запрос и добавляет фактическое время и число строк                                 |
| `BUFFERS`         | Добавляет число прочитанных страниц. В PostgreSQL 18 включается автоматически вместе с `ANALYZE` |

**Важно: `EXPLAIN ANALYZE` выполняет запрос.** Для `INSERT` / `UPDATE` / `DELETE` используйте транзакцию с откатом:

```sql
BEGIN;
EXPLAIN ANALYZE UPDATE orders SET status = 'cancelled' WHERE id = 1;
ROLLBACK;
```

> Выполняйте блок целиком. Если в режиме Auto-Commit выполнить только строку `EXPLAIN ANALYZE UPDATE ...`, изменение зафиксируется.

### 3.1. Как читать план

План — дерево операций (узлов). Нижние узлы читают таблицы, верхние соединяют, группируют и сортируют.
**Читайте снизу вверх:** узел со стрелкой `->` выполняется раньше узла над ним.

Пример из eshop: заказы за 30 дней, индекса по дате нет.

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE created_at > now() - interval '30 days';
```

```text
Seq Scan on orders  (cost=0.00..5288.00 rows=8083 width=39)
                    (actual time=0.007..29.090 rows=8124.00 loops=1)
  Filter: (created_at > (now() - '30 days'::interval))
  Rows Removed by Filter: 191876
  Buffers: shared hit=1788
Execution Time: 29.359 ms
```

| Что видим                        | Что это значит                                                         |
| -------------------------------- | ---------------------------------------------------------------------- |
| `Seq Scan on orders`             | Таблица прочитана целиком                                              |
| `rows=8083` рядом с `cost`       | **Оценка** планировщика: ожидал 8 083 строки                           |
| `rows=8124` рядом с `actual`     | **Факт**: вернулось 8 124 строки. Оценка близка — статистика актуальна |
| `Rows Removed by Filter: 191876` | 96 % прочитанных строк выброшены                                       |
| `Buffers: shared hit=1788`       | Прочитаны 1 788 страниц — вся таблица (≈ 14 МБ)                        |
| `Execution Time`                 | Время выполнения. Используйте для сравнения вариантов                  |

> Все элементы строки плана — справочник, С.3.

### 3.2. Четыре вопроса к плану

| №   | Вопрос                             | Где смотреть                           | Тревожный признак                                    |
| --- | ---------------------------------- | -------------------------------------- | ---------------------------------------------------- |
| 1   | Где тратится время?                | `actual time` узлов (с учётом `loops`) | Один узел занимает почти всё время                   |
| 2   | Верно ли планировщик оценил объём? | `rows` оценка ↔ `rows` факт            | Расхождение в 10 раз и более — устаревшая статистика |
| 3   | Сколько прочитано зря?             | `Rows Removed by Filter`               | Выброшено намного больше, чем возвращено             |
| 4   | Сколько раз повторяется узел?      | `loops`                                | Большое `loops` у Seq Scan внутри Nested Loop        |

### Упражнение 2. Найдите проблему

Запрос лаб. 06, п. 2.3: заказы клиентов региона MSK за 30 дней с суммой позиций. Индексов нет (сокращено):

```text
Hash Join  (Hash Cond: o.customer_id = c.id)
  ->  Parallel Hash Join  (Hash Cond: oi.order_id = o.id)
        ->  Parallel Seq Scan on order_items oi   (rows=200000.00 loops=3)
        ->  Parallel Seq Scan on orders o          (Rows Removed by Filter: 191886)
  ->  Seq Scan on customers c                      (Rows Removed by Filter: 18993)
Execution Time: 197.607 ms
```

Результат запроса — около 410 заказов и 1 230 позиций. Какая таблица читается зря и что поможет?

<details>
<summary>Ответ</summary>

- `order_items`: прочитаны все 600 000 строк (`200000 × loops=3`) ради ≈ 1 230 позиций. Нужен индекс по `order_items(order_id)`.
- `orders`: выброшено 191 886 строк из 200 000. Поможет индекс по `orders(created_at)`.
- `customers`: выброшено 18 993 из 20 000. Поможет индекс по `customers(region)`.

`loops=3` — параллельный план: 2 рабочих процесса и ведущий (справочник, С.5).

</details>

## 4. Исправить: когда индекс помогает, а когда нет

### 4.1. Индекс помогает

Тот же запрос после создания индексов `customers(region)`, `orders(created_at)`, `order_items(order_id)` (сокращено):

```text
Nested Loop
  ->  Hash Join  (Hash Cond: o.customer_id = c.id)
        ->  Bitmap Heap Scan on orders o
              ->  Bitmap Index Scan on idx_orders_created_at
        ->  Bitmap Heap Scan on customers c
              ->  Bitmap Index Scan on idx_customers_region
  ->  Index Scan using idx_order_items_order on order_items oi  (rows=3.00 loops=411)
Execution Time: 16.229 ms
```

В 12 раз быстрее в эталонном прогоне; на другом компьютере — примерно в 8–12 раз.
Позиции 411 заказов найдены по индексу: 411 циклов по 3 строки вместо чтения 600 000.

Индекс `orders(customer_id)` тоже был создан, но планировщик его не выбрал: путь через фильтр по дате дешевле.
**Созданный индекс не гарантирует его использование.**

> Число заказов за 30 дней зависит от момента запуска, время — от компьютера.
> Сравнивайте отношение «без индексов / с индексами» и форму плана, а не миллисекунды.

### 4.2. Индекс не поможет

```text
Seq Scan on orders o  (actual time=0.123..2795.456 rows=2412345 loops=1)
  Filter: (created_at > '2024-01-01 00:00:00+03'::timestamp with time zone)
  Rows Removed by Filter: 87655
  Buffers: shared read=93000
```

Фильтр выбрасывает всего 3,5 % строк: запросу нужна почти вся таблица (2,4 млн строк).
Индекс заставил бы читать почти все страницы, да ещё вразнобой. Seq Scan здесь — правильный выбор.
Ускорить такой запрос может только **другая постановка задачи** (п. 5.3).

### Упражнение 3. Поможет ли индекс?

| План       | Вернул строк | Выброшено фильтром | Поможет индекс? |
| ---------- | ------------ | ------------------ | --------------- |
| А (п. 3.1) | 8 124        | 191 876            |                 |
| Б (п. 4.2) | 2 412 345    | 87 655             |                 |

<details>
<summary>Ответ</summary>

- **А — да.** Нужно 4 % строк, выброшено 96 %. Индекс по `created_at` прочитает только нужные страницы.
- **Б — нет.** Нужно 96,5 % строк. Индекс не уменьшит объём чтения.

Правило: смотрите на соотношение «вернул / выброшено», а не на время.

</details>

### 4.3. Проверить

1. Сбросить статистику: `SELECT pg_stat_statements_reset();`
2. Повторить `EXPLAIN (ANALYZE, BUFFERS)`: изменились ли узел, `Buffers`, `Execution Time`?
3. Через рабочий период проверить строку запроса в `pg_stat_statements`: упали ли `mean_exec_time` и `total_exec_time`?

## 5. Требования к производительности

### 5.1. Объём данных и рост

Почему «на тестовом стенде всё быстро» (вопрос 2 кейса): на сотнях строк таблица занимает 1–2 страницы,
и любой запрос выполняется за доли миллисекунды (лаб. 06, «Почему нужен большой объём данных»).

| Способ доступа                    | Как растёт время с ростом таблицы                                                          |
| --------------------------------- | ------------------------------------------------------------------------------------------ |
| Seq Scan                          | Примерно пропорционально размеру таблицы: в 10 раз больше строк — примерно в 10 раз дольше |
| Поиск по индексу нескольких строк | Почти не меняется: дерево индекса становится выше на 1 уровень при росте в сотни раз       |

Пример: Seq Scan по `orders` из п. 3.1 — 1 788 страниц, ≈ 29 мс на 200 000 строк.
При 2 млн строк — ≈ 18 000 страниц и, по оценке, ≈ 300 мс, если таблица в памяти, и дольше, если чтение идёт с диска.

**Следствия для требований:**

- указывайте объём данных и рост: «при 2 млн заказов и росте 50 000 в месяц»;
- проводите приёмку на объёме, близком к production. Тест на пустой базе ничего не доказывает.

### 5.2. Среднее скрывает хвост

`pg_stat_statements` даёт среднее (`mean_exec_time`), разброс (`stddev_exec_time`) и максимум (`max_exec_time`).
Среднее 50 мс при максимуме 4 с значит: часть пользователей ждёт секунды.

Требование пишут через **перцентиль**: «95 % открытий экрана — не дольше 300 мс» (p95 ≤ 300 мс).
Перцентили дают системы мониторинга приложения (APM) и нагрузочные тесты. Большой `stddev_exec_time`
в `pg_stat_statements` — сигнал, что хвост есть (справочник, С.2).

### 5.3. Сколько данных на самом деле нужно

- **Ограничение объёма.** Экран показывает 50 строк — запрос должен вернуть 50 строк (`LIMIT`, постраничный вывод), а не 2,4 млн.
- **Итоги вместо строк.** Отчёту «выручка по месяцам» нужны 12 чисел, а не все заказы года: агрегирование (`GROUP BY`) выполняется в базе.
- **Только нужные столбцы.** `SELECT *` передаёт лишние данные и мешает Index Only Scan.

**Шаблон требования:**

> Экран «Заказы клиента»: p95 ≤ 300 мс, p99 ≤ 1 с при 2 млн заказов, росте 50 000 заказов в месяц и 50 одновременных пользователях.
> Показывается 50 последних заказов с постраничным переходом. Приёмка — нагрузочный тест на копии данных production-объёма.

## 6. Передать DBA

DBA не может воспроизвести вашу ситуацию без контекста. Передайте всё одним документом.

```markdown
## Запрос для анализа

### Запрос (полный текст, с реальными значениями параметров)
SELECT o.id, c.name, o.total_amount
FROM   orders o
JOIN   customers c ON o.customer_id = c.id
WHERE  o.created_at > '2024-01-01'
ORDER  BY o.total_amount DESC;

### Окружение
- Версия: PostgreSQL 18.0 (SELECT version();)
- База: eshop
- work_mem = 4MB, shared_buffers = 128MB

### Таблицы
- orders: 2,5 млн строк, 730 МБ (pg_relation_size)
- Индексы orders: orders_pkey (id), idx_orders_customer_id (customer_id)

### Статистика (строка из pg_stat_statements)
- calls = 500 в сутки, mean_exec_time = 4 500 мс, stddev = 300 мс
- (shared_blks_hit + shared_blks_read) / calls = 93 000 страниц

### Вывод EXPLAIN (ANALYZE, BUFFERS)
[полный вывод, без сокращений]

### Наблюдения
- Seq Scan на orders, Rows Removed by Filter = 87 655 из 2,5 млн:
  фильтр по created_at отсекает 3,5 % строк, запрос возвращает 2,4 млн строк
- Buffers: read = 93 000 при повторных запусках — таблица больше кэша

### Ожидание
Запрос должен выполняться < 200 мс (SLA отчёта).
```

Правила:

- **Полный план, без сокращений.** Важные детали часто в глубине дерева.
- **Реальные значения параметров**, а не `$1`. План зависит от значений.
- **Разделяйте источники:** `shared_blks_read` — колонка `pg_stat_statements` (сумма за все вызовы); `Buffers: read` — строка плана (один вызов).

### Упражнение 4. Что не так с этим обращением?

<details>
<summary>Ответ</summary>

Запрос возвращает 2,4 млн строк с сортировкой. Никакой индекс не даст 200 мс: одна передача такого объёма клиенту занимает больше.
Прежде чем писать DBA, аналитик проверяет требование (п. 5.3): нужны ли отчёту все строки?
Обычно нужны первые N (`LIMIT`, постраничный вывод) или итоги (`GROUP BY`). Тогда запрос меняется, и SLA становится достижимым.

</details>

## 7. Что было вчера: журнал, auto_explain, pgBadger

`pg_stat_statements` хранит сводные цифры с момента сброса. Вопрос кейса «что было вчера после обеда» он не решает:
в нём нет времени выполнения и значений параметров.

| Вопрос                                                  | Инструмент                    |
| ------------------------------------------------------- | ----------------------------- |
| Что выполняется прямо сейчас?                           | `pg_stat_activity` (лекция 7) |
| Какой запрос самый дорогой за период?                   | `pg_stat_statements`          |
| Почему этот запрос медленный?                           | `EXPLAIN (ANALYZE, BUFFERS)`  |
| Что было медленным вчера в 15:20, с какими параметрами? | Журнал сервера + **pgBadger** |
| Какой был план у вчерашнего медленного запроса?         | **auto_explain**              |

- **Журнал сервера.** При `log_min_duration_statement = 500` каждый запрос дольше 500 мс записывается в журнал: время, пользователь, текст, параметры.
- **pgBadger** читает журнал и строит HTML-отчёт: самые медленные и самые частые запросы, графики нагрузки по часам, ошибки, блокировки.
- **auto_explain** записывает в журнал **план** медленного запроса. Повторять запрос вручную не нужно: план уже есть, с фактическими значениями на момент выполнения.

## С.2. pg_stat_statements: колонки и особенности

| Колонка            | Значение                                                                          |
| ------------------ | --------------------------------------------------------------------------------- |
| `calls`            | Число выполнений                                                                  |
| `total_exec_time`  | Суммарное время, мс. Показывает общую нагрузку на сервер                          |
| `mean_exec_time`   | Среднее время одного выполнения, мс                                               |
| `stddev_exec_time` | Разброс времени. Большое значение — время нестабильно                             |
| `max_exec_time`    | Самое долгое выполнение, мс                                                       |
| `rows`             | Суммарное число возвращённых или изменённых строк                                 |
| `shared_blks_hit`  | Страницы (8 КБ), найденные в shared_buffers                                       |
| `shared_blks_read` | Страницы, которых не было в shared_buffers. Они пришли с диска **или из кэша ОС** |

Фильтры запроса из п. 2.1:

- `dbid` — представление содержит статистику всех баз кластера;
- `pg_catalog` — исключает служебные запросы клиентов (DBeaver, pgAdmin);
- `pg_stat` — исключает сам запрос к `pg_stat_statements`.

> `total_exec_time` — время выполнения запроса. Время планирования в него не входит: оно учитывается отдельно (`total_plan_time`) при `pg_stat_statements.track_planning = on`.
> Отправка строк клиенту входит: если клиент читает результат медленно, сервер ждёт, и время выполнения растёт.

> Представление хранит до `pg_stat_statements.max` разных запросов (по умолчанию 5 000). При переполнении редкие запросы вытесняются. Число вытеснений и время последнего сброса показывает `SELECT * FROM pg_stat_statements_info;`. Частые вытеснения — повод увеличить `max`.

**Почему `shared_blks_read` остаётся большим при повторных запусках.** Если таблица больше ¼ shared_buffers (по умолчанию 128 МБ / 4 = 32 МБ), Seq Scan помещает прочитанные страницы не в общий кэш, а в малый кольцевой буфер (≈ 256 КБ). Так большой просмотр не вытесняет из кэша другие данные. Следствие: страницы такой таблицы почти не остаются в shared_buffers, и каждый Seq Scan снова даёт `read`. В eshop это `order_items` (≈ 39 МБ).

**Нестабильные запросы:**

```sql
SELECT LEFT(regexp_replace(query, '\s+', ' ', 'g'), 80) AS query_preview,
       calls,
       ROUND(mean_exec_time::numeric, 1)   AS avg_ms,
       ROUND(stddev_exec_time::numeric, 1) AS stddev_ms,
       ROUND(max_exec_time::numeric, 1)    AS max_ms,
       ROUND((stddev_exec_time / NULLIF(mean_exec_time, 0))::numeric, 2) AS cv
FROM   pg_stat_statements
WHERE  dbid = (SELECT oid FROM pg_database WHERE datname = current_database())
  AND  calls >= 5          -- на рабочем сервере: >= 100
ORDER  BY cv DESC NULLS LAST
LIMIT  10;
```

`cv` (коэффициент вариации) = stddev / mean. Значение больше 1 означает, что время сильно меняется от вызова к вызову.

Возможные причины:

- первые вызовы читают данные вне кэша, следующие — из кэша;
- разные значения параметров `$1` отбирают разное число строк;
- конкуренция с другими сеансами за блокировки, CPU, диск.

> Порог `calls >= 5` подходит для учебного стенда. На рабочем сервере используйте `>= 100`: при малом числе вызовов статистика ненадёжна.

## С.3. Элементы строки плана

| Элемент                             | Значение                                                                                                                     |
| ----------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| `cost=0.00..5288.00`                | Оценочная стоимость в условных единицах: до первой строки .. до последней. Используется только для сравнения вариантов плана |
| `rows=8083` (в скобках `cost`)      | **Оценка** планировщика: число строк. Для параллельного узла — на один процесс (С.5)                                         |
| `width=39`                          | Средний размер строки, байт                                                                                                  |
| `actual time=0.007..29.090`         | Фактическое время, мс: до первой строки .. до последней. **На один цикл**. **Включает время дочерних узлов**                 |
| `rows=8124.00` (в скобках `actual`) | **Фактическое** число строк на один цикл (среднее, поэтому дробное)                                                          |
| `loops=1`                           | Сколько раз узел выполнен. Всего строк = `rows × loops`                                                                      |
| `Filter`                            | Условие, которое проверяется для каждой прочитанной строки                                                                   |
| `Rows Removed by Filter`            | Сколько строк прочитано зря. Большое значение при Seq Scan — индекс может помочь                                             |
| `Buffers: shared hit`               | Страницы из shared_buffers                                                                                                   |
| `Buffers: shared read`              | Страницы вне shared_buffers (диск или кэш ОС)                                                                                |
| `Planning Time`                     | Время построения плана. Большое значение при первом запуске — каталог не в кэше                                              |
| `Execution Time`                    | Время выполнения. Используйте для сравнения вариантов                                                                        |

**Собственное время узла** = (`actual time` × `loops`) узла − сумма (`actual time` × `loops`) его дочерних узлов. Узел с наибольшим собственным временем — узкое место.

> Для параллельных узлов (С.5) не умножайте на `loops`: процессы работают одновременно, и `actual time` уже близко к реальному времени выполнения узла.

**`loops` больше 1** встречается в двух случаях:

- внутренний узел Nested Loop: выполняется по разу на каждую строку внешнего узла;
- параллельный план: по разу в каждом процессе (С.5).

## С.4. Основные узлы плана

**Доступ к таблице**

| Узел                                     | Что делает                                                                                                                            | Когда появляется                                                                                                |
| ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `Seq Scan`                               | Читает все страницы таблицы по порядку                                                                                                | Нет подходящего индекса, таблица мала или нужна большая часть строк                                             |
| `Index Scan`                             | Находит строки по индексу, читает их страницы таблицы                                                                                 | Отбирается очень малая часть строк (доли процента), или нужен порядок индекса (`ORDER BY … LIMIT`)              |
| `Index Only Scan`                        | Берёт данные из индекса. Таблицу читает только для страниц, которые не отмечены как полностью видимые (строка `Heap Fetches` в плане) | Все нужные колонки есть в индексе. Эффективен после `VACUUM`                                                    |
| `Bitmap Index Scan` + `Bitmap Heap Scan` | Собирает по индексу карту страниц, затем читает их по порядку, каждую один раз                                                        | Строк сотни–тысячи (примерно от долей процента до 10–20 %) или несколько условий через `BitmapAnd` / `BitmapOr` |

> Границы между узлами приблизительные. Планировщик сравнивает стоимость вариантов, а не процент строк.
> В лаб. 06 (п. 2.4) ≈ 8 100 заказов за 30 дней (4 %) читаются через Bitmap Heap Scan, а позиции одного заказа (3 строки) — через Index Scan.

**Соединение**

| Узел          | Что делает                                                           | Когда появляется                                             |
| ------------- | -------------------------------------------------------------------- | ------------------------------------------------------------ |
| `Nested Loop` | Для каждой строки внешнего набора ищет строки во внутреннем          | Внешний набор мал, по внутреннему есть индекс                |
| `Hash Join`   | Строит хеш-таблицу по одному набору, проверяет по ней строки другого | Большие наборы, равенство в условии соединения               |
| `Merge Join`  | Сливает два набора, отсортированных по ключу соединения              | Оба набора отсортированы по ключу: по индексу или узлом Sort |

**Обработка результата**

| Узел             | Что делает                             | Когда появляется                                     |
| ---------------- | -------------------------------------- | ---------------------------------------------------- |
| `Sort`           | Сортирует строки                       | ORDER BY, подготовка к GroupAggregate или Merge Join |
| `HashAggregate`  | Группирует через хеш-таблицу           | GROUP BY, строки не отсортированы                    |
| `GroupAggregate` | Группирует отсортированный поток       | GROUP BY, строки отсортированы                       |
| `Limit`          | Останавливает выполнение после N строк | LIMIT                                                |

## С.5. Параллельные планы

Для таблиц больше 8 МБ (`min_parallel_table_scan_size`) PostgreSQL может запустить дополнительные рабочие процессы (parallel workers). Каждый процесс читает свою часть страниц. Ведущий процесс тоже участвует и объединяет результаты.

Пример — запрос Q3 лаб. 06 (продажи по товарам), сокращено:

```text
Gather Merge  (... rows=2400 ...) (actual ... rows=3000.00 loops=1)
  Workers Planned: 2
  Workers Launched: 2
  ->  Sort  (... rows=1000 ...) (actual ... rows=1000.00 loops=3)
        ->  Partial HashAggregate  (...)
              ->  Parallel Seq Scan on order_items  (cost=0.00..7500.00 rows=250000 width=12)
                                                    (actual ... rows=200000.00 loops=3)
```

| Элемент                                | Значение                                                                  |
| -------------------------------------- | ------------------------------------------------------------------------- |
| `Gather` / `Gather Merge`              | Собирает строки от процессов. `Gather Merge` сохраняет порядок сортировки |
| `Parallel Seq Scan`                    | Каждый процесс читает часть страниц таблицы                               |
| `Partial ...` / `Finalize ...`         | Агрегация в 2 этапа: частичная в каждом процессе, итоговая в ведущем      |
| `Workers Planned` / `Workers Launched` | Сколько процессов запланировано / запущено                                |
| `loops=3`                              | 2 рабочих процесса + ведущий                                              |

**Оценка `rows` в параллельном узле.** Для 2 рабочих процессов планировщик делит число строк на 2,4: он учитывает, что ведущий процесс участвует частично. Таблица 600 000 строк → оценка `rows=250000`, факт `rows=200000 loops=3`. Это **не** ошибка статистики.

**`Workers Launched` меньше `Workers Planned`** — свободных процессов не хватило, или клиент получает результат порциями (fetch size, например в DBeaver). Тогда работу выполняет ведущий процесс, и запрос идёт медленнее.

## С.6. Признаки проблем в плане

| Признак                                                                   | Интерпретация                                                               | Действие                                                                     |
| ------------------------------------------------------------------------- | --------------------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Оценка `rows` отличается от факта в 10 раз и более (не параллельный узел) | Устаревшая статистика или зависимые условия                                 | `ANALYZE table_name;`. Для зависимых колонок — `CREATE STATISTICS`           |
| Seq Scan на большой таблице с большим `Rows Removed by Filter`            | Нет подходящего индекса                                                     | Создать индекс по колонке фильтра                                            |
| Seq Scan на большой таблице без фильтра                                   | Запросу нужны все строки                                                    | Индекс не поможет. Переписать запрос, материализованное представление        |
| `Hash` или `HashAggregate` с `Batches: 4` (больше 1)                      | Хеш-таблица не поместилась в память, данные записаны на диск                | Увеличить `work_mem` для сеанса                                              |
| `Sort Method: external merge  Disk: 4096kB`                               | Сортировка вышла на диск                                                    | Увеличить `work_mem` для сеанса                                              |
| Nested Loop с большим `loops` у внутреннего Seq Scan                      | Внутренняя таблица читается целиком на каждую строку                        | Индекс по колонке соединения                                                 |
| Много `shared read` при повторных запусках                                | Данные не помещаются в кэш или таблица читается через кольцевой буфер (С.2) | Уменьшить объём чтения (индекс). Изменение `shared_buffers` — обсудить с DBA |

> Лимит памяти: `work_mem` (по умолчанию 4 МБ) для сортировки; `work_mem × hash_mem_multiplier` (4 МБ × 2 = 8 МБ) для хеш-операций. Лимит действует на **каждый** узел каждого запроса. Глобальное увеличение `work_mem` опасно: при многих сеансах сервер может исчерпать память.

## С.8. auto_explain: настройка

**Для одного сеанса** — учебный стенд и разовая проверка. Перезапуск не нужен.

```sql
LOAD 'auto_explain';                    -- права суперпользователя
SET auto_explain.log_min_duration = 0;  -- план каждого запроса
SET auto_explain.log_analyze = on;
SET auto_explain.log_buffers = on;
SET client_min_messages = log;          -- показать план в клиенте
```

**Постоянно для сервера:**

```sql
ALTER SYSTEM SET shared_preload_libraries = 'pg_stat_statements,auto_explain';
ALTER SYSTEM SET auto_explain.log_min_duration = '1s';  -- запросы дольше 1 с
ALTER SYSTEM SET auto_explain.log_analyze = on;
ALTER SYSTEM SET auto_explain.log_buffers = on;
ALTER SYSTEM SET auto_explain.log_timing = off;         -- см. ниже
ALTER SYSTEM SET auto_explain.log_nested_statements = on;
-- перезапуск сервера
```

> **Накладные расходы `log_analyze`.** Сервер не знает заранее, превысит ли запрос порог. Поэтому при `log_analyze = on` сбор фактических данных включается для **каждого** запроса, а не только для медленных. Самая дорогая часть — замер времени для каждой строки каждого узла. На рабочем сервере:
> - `auto_explain.log_timing = off` — строки и Buffers остаются, время по узлам не замеряется;
> - `auto_explain.sample_rate = 0.1` — анализировать только 10 % запросов.

`log_nested_statements = on` — записывать также запросы внутри функций и процедур.

**Пример записи в журнале** (план из п. 4.2 целиком):

```text
2026-10-08 15:22:33 MSK [5678]: user=app,db=eshop,app=crm,client=10.0.0.5 LOG:  duration: 3451.234 ms  plan:
	Query Text: SELECT o.id, c.name FROM orders o JOIN customers c ON o.customer_id = c.id
	            WHERE o.created_at > '2024-01-01'
	Hash Join  (cost=617.00..157553.00 rows=2400000 width=40) (actual time=6.112..3302.910 rows=2412345 loops=1)
	  Hash Cond: (o.customer_id = c.id)
	  Buffers: shared hit=167 read=93000
	  ->  Seq Scan on orders o  (cost=0.00..124250.00 rows=2400000 width=16) (actual time=0.123..2795.456 rows=2412345 loops=1)
	        Filter: (created_at > '2024-01-01 00:00:00+03'::timestamp with time zone)
	        Rows Removed by Filter: 87655
	        Buffers: shared read=93000
	  ->  Hash  (cost=367.00..367.00 rows=20000 width=32) (actual time=5.801..5.802 rows=20000 loops=1)
	        Buckets: 32768  Batches: 1  Memory Usage: 1450kB
	        Buffers: shared hit=167
	        ->  Seq Scan on customers c  (cost=0.00..367.00 rows=20000 width=32) (actual time=0.010..2.215 rows=20000 loops=1)
	              Buffers: shared hit=167
```

Время уходит на `Seq Scan on orders` (2,8 с из 3,3 с), страницы читаются вне кэша (`read=93000`).

## С.9. pgBadger: журнал, установка, отчёт

**Отличие от `pg_stat_statements`:**

|                 | pg_stat_statements                        | pgBadger                                                                                |
| --------------- | ----------------------------------------- | --------------------------------------------------------------------------------------- |
| Источник        | Память сервера                            | Файлы журнала                                                                           |
| Данные          | Сводные (сумма, среднее) по всем запросам | Каждый запрос, записанный в журнал (дольше порога), с моментом выполнения и параметрами |
| Ответ на вопрос | «Какой запрос самый дорогой?»             | «Что было медленным вчера в 15:20?»                                                     |
| Требует         | Расширение                                | Настроенный журнал                                                                      |

### С.9.1. Требования к журналу

```sql
ALTER SYSTEM SET logging_collector = on;   -- запись в файлы (требует перезапуска)
ALTER SYSTEM SET log_line_prefix = '%t [%p]: user=%u,db=%d,app=%a,client=%h ';
ALTER SYSTEM SET lc_messages = 'C';        -- сообщения на английском
ALTER SYSTEM SET log_min_duration_statement = 500;  -- запросы дольше 500 мс
SELECT pg_reload_conf();
```

- `logging_collector` — в установке PostgreSQL для Windows включён по умолчанию.
- `log_line_prefix` — формат префикса строки (см. лекцию 7). pgBadger определяет по нему время, пользователя, базу.
- `lc_messages = 'C'` — **обязательно для русской локали.** pgBadger ищет английские строки `duration:`, `statement:`. С русскими сообщениями отчёт будет пустым.
- `log_min_duration_statement` — порог записи запросов. `0` — все запросы (только для учебного стенда: журнал быстро растёт). В лаб. 06 используется `0`, после работы значение возвращается к `500`.

> `lc_messages` и `log_line_prefix` после `pg_reload_conf()` действуют для **новых** сеансов. Переподключитесь, прежде чем создавать нагрузку.

Для полного отчёта (блокировки, временные файлы, контрольные точки, автоочистка) включите также:

```sql
ALTER SYSTEM SET log_lock_waits = on;                  -- ожидания блокировок дольше deadlock_timeout
ALTER SYSTEM SET log_temp_files = 0;                   -- все временные файлы (выход сортировок и хешей на диск)
ALTER SYSTEM SET log_checkpoints = on;
ALTER SYSTEM SET log_autovacuum_min_duration = 0;
SELECT pg_reload_conf();
```

`log_temp_files = 0` связывает журнал с С.6: каждая запись — запрос, которому не хватило `work_mem`.

### С.9.2. Установка и запуск в Windows

pgBadger — программа на языке Perl. В Windows Perl не встроен, поэтому сначала устанавливается интерпретатор,
затем скрипт pgBadger. Сам PostgreSQL для pgBadger не нужен: программа читает только файл журнала.

```mermaid
flowchart LR
    PG[PostgreSQL] -->|пишет| LOG[Файл журнала<br/>data\log\*.log]
    LOG -->|читает| PB[pgBadger<br/>perl-скрипт]
    PB -->|строит| HTML[Отчёт<br/>report.html]
```

**Шаг 1. Установить Strawberry Perl.**

1. Скачайте установщик `.msi` с https://strawberryperl.com/ (64-bit).
2. Запустите и оставьте параметры по умолчанию. Установщик сам добавит Perl в `PATH`.
3. Откройте **новое** окно PowerShell (старое не видит изменение `PATH`) и проверьте:

```powershell
perl -v
```

**Шаг 2. Скачать pgBadger.**

1. Откройте https://github.com/darold/pgbadger/releases → последний релиз → **Source code (zip)**.
2. Распакуйте архив. Внутри — папка вида `pgbadger-13.x`.
3. Переименуйте или переместите её так, чтобы получилось `C:\pgbadger`.
   Файл `pgbadger` **без расширения** должен лежать по пути `C:\pgbadger\pgbadger`.
4. Проверьте:

```powershell
perl C:\pgbadger\pgbadger --version
```

> Установка не нужна: pgBadger — один скрипт, Perl выполняет его напрямую.

**Шаг 3. Подготовить журнал и создать нагрузку.**

1. Выполните настройки из С.9.1.
2. **Переподключитесь** в DBeaver: `lc_messages` и `log_line_prefix` действуют только для новых сеансов.
3. Выполните запросы, которые хотите проанализировать (в лаб. 06 — Q1–Q3 по 5–10 раз).

> pgBadger понимает формат `%t [%p]: user=%u,db=%d,app=%a,client=%h ` без дополнительных параметров.
> Если в вашей установке другой `log_line_prefix`, передайте его программе: `--prefix '<значение>'`.

**Шаг 4. Найти файл журнала.**

```sql
SELECT current_setting('data_directory') AS data_dir,
       pg_current_logfile()              AS current_log;
```

`current_log` — путь **относительно** каталога данных. Полный путь = `data_dir` + `\` + `current_log`,
например `C:\Program Files\PostgreSQL\18\data\log\postgresql-2026-10-08_002924.log`.

Список всех файлов журнала, новые сверху (PowerShell от имени администратора):

```powershell
$logDir = "C:\Program Files\PostgreSQL\18\data\log"
Get-ChildItem $logDir -Filter *.log | Sort-Object LastWriteTime -Descending |
    Select-Object Name, Length, LastWriteTime
```

> Каталог `data` закрыт для обычных пользователей. Без прав администратора будет ошибка «Отказано в доступе».

**Шаг 5. Построить отчёт** (PowerShell от имени администратора).

Один файл:

```powershell
perl C:\pgbadger\pgbadger "$logDir\postgresql-2026-10-08_002924.log" -o $env:TEMP\report.html
```

Несколько файлов. PowerShell не раскрывает маску `*` для внешних программ, поэтому сначала соберите список файлов:

```powershell
$files = (Get-ChildItem $logDir -Filter *.log).FullName
perl C:\pgbadger\pgbadger $files -o $env:TEMP\report.html
```

| Параметр     | Значение                                                                             |
| ------------ | ------------------------------------------------------------------------------------ |
| путь к файлу | Один или несколько файлов журнала                                                    |
| `-o`         | Куда записать отчёт. Расширение `.html` — формат HTML                                |
| `--prefix`   | Формат `log_line_prefix`, если он нестандартный                                      |
| `-b` / `-e`  | Начало / конец периода, например `-b "2026-10-08 15:00:00" -e "2026-10-08 16:00:00"` |

**Шаг 6. Открыть отчёт.**

```powershell
Start-Process $env:TEMP\report.html
```

| Раздел отчёта                  | Что показывает                                                                                      | Аналог в `pg_stat_statements`                 |
| ------------------------------ | --------------------------------------------------------------------------------------------------- | --------------------------------------------- |
| **Slowest individual queries** | Самые медленные отдельные выполнения: время, момент, пользователь, **реальные значения параметров** | `max_exec_time` (но без момента и параметров) |
| **Time consuming queries**     | Запросы с наибольшим **суммарным** временем                                                         | Сортировка по `total_exec_time`               |
| **Most frequent queries**      | Самые частые запросы                                                                                | Сортировка по `calls`                         |

Другие разделы: **Errors** (ошибки), **Locks** (ожидания блокировок), **Temporary files** (запросы, которым не хватило `work_mem`),
**Checkpoints**, **Vacuums**. Они заполняются, если включены параметры из конца С.9.1.

**Типичные проблемы:**

| Симптом                                  | Причина                                                                                 | Решение                                               |
| ---------------------------------------- | --------------------------------------------------------------------------------------- | ----------------------------------------------------- |
| `perl` не является именем командлета     | Окно PowerShell открыто до установки Perl                                               | Открыть новое окно PowerShell                         |
| «Отказано в доступе» к файлу журнала     | Нет прав на каталог `data`                                                              | Запустить PowerShell от имени администратора          |
| Отчёт пустой (нет запросов)              | `lc_messages` не `C`, или `log_min_duration_statement = -1`, или сеанс не переподключён | Проверить С.9.1, переподключиться, повторить нагрузку |
| Отчёт пустой, в журнале есть `duration:` | Нестандартный `log_line_prefix`                                                         | Указать `--prefix`                                    |
| Нет данных за нужное время               | Журнал разбит на несколько файлов                                                       | Передать все файлы (шаг 5)                            |

**Шаг 7. Вернуть настройки.** `log_min_duration_statement = 0` записывает каждый запрос и быстро заполняет диск (лаб. 06, п. 3.4):

```sql
ALTER SYSTEM SET log_min_duration_statement = 500;
SELECT pg_reload_conf();
```

## С.10. Словарь терминов

**Хранение и память**

| Термин                | Определение                                                                                                                                            |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Страница (блок)       | Единица хранения данных: 8 КБ. Таблицы и индексы состоят из страниц. PostgreSQL читает и записывает данные страницами, а не строками                   |
| `shared_buffers`      | Общий кэш PostgreSQL в оперативной памяти. Хранит недавно прочитанные страницы. По умолчанию 128 МБ                                                    |
| Кэш ОС                | Кэш файлов операционной системы. Страница, которой нет в `shared_buffers`, может прийти отсюда, а не с диска                                           |
| Кольцевой буфер       | Небольшой (≈ 256 КБ) отдельный буфер для полного чтения большой таблицы. Не даёт одному большому чтению вытеснить из `shared_buffers` остальные данные |
| `work_mem`            | Память на одну операцию сортировки или хеширования в запросе. По умолчанию 4 МБ                                                                        |
| `hash_mem_multiplier` | Множитель `work_mem` для хеш-операций. По умолчанию 2: хеш-таблица может занять 8 МБ                                                                   |
| Временный файл        | Файл на диске, куда сортировка или хеш-таблица сбрасывает данные, если не хватило `work_mem`. Резко замедляет запрос                                   |

**Настройка сервера**

| Термин                     | Определение                                                                                                                                    |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Расширение (extension)     | Дополнительный модуль PostgreSQL: добавляет функции и представления. Подключается командой `CREATE EXTENSION` в конкретной базе                |
| `shared_preload_libraries` | Список библиотек, которые сервер загружает при старте. Изменение требует перезапуска                                                           |
| `ALTER SYSTEM`             | Команда записи параметра в файл `postgresql.auto.conf` без ручной правки файлов. Значения из этого файла имеют приоритет над `postgresql.conf` |
| `pg_reload_conf()`         | Перечитать конфигурацию без перезапуска. Действует не для всех параметров                                                                      |
| `pending_restart`          | Признак в `pg_settings`: параметр записан, но применится только после перезапуска                                                              |
| Суперпользователь          | Роль с полными правами (например, `postgres`). Нужна для `LOAD`, `ALTER SYSTEM`                                                                |
| Auto-Commit                | Режим клиента: каждая команда сразу фиксируется отдельной транзакцией                                                                          |
| DML                        | Команды изменения данных: `INSERT`, `UPDATE`, `DELETE`                                                                                         |

**Статистика запросов**

| Термин                            | Определение                                                                                                                                          |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pg_stat_statements`              | Расширение, которое накапливает статистику по всем выполненным запросам: число вызовов, время, прочитанные страницы                                  |
| Нормализация запроса              | Замена констант параметрами: `status = 'pending'` → `status = $1`. Запросы, которые отличаются только константами, попадают в одну строку статистики |
| Вытеснение (dealloc)              | Удаление редких запросов из статистики, когда достигнут предел `pg_stat_statements.max`                                                              |
| Стандартное отклонение (`stddev`) | Мера разброса времени выполнения вокруг среднего                                                                                                     |
| Коэффициент вариации (`cv`)       | `stddev / mean`. Разброс относительно среднего. `cv > 1` — время сильно меняется от вызова к вызову                                                  |
| Проблема N+1                      | 1 запрос за списком и ещё по 1 запросу на каждый элемент списка. Каждый запрос быстрый, но их много                                                  |
| ORM                               | Библиотека в приложении, которая строит SQL-запросы по объектам программы. Частый источник N+1                                                       |
| Перцентиль (p95)                  | Значение, которое не превышают 95 % измерений. «p95 ≤ 300 мс» — 95 % запросов не дольше 300 мс                                                       |
| SLA                               | Соглашение об уровне сервиса: согласованное требование, например «отчёт строится не дольше 200 мс»                                                   |
| APM                               | Система мониторинга приложения: измеряет время ответа экранов и запросов, считает перцентили                                                         |

**План выполнения**

| Термин                        | Определение                                                                                                                                                    |
| ----------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Планировщик (оптимизатор)     | Часть PostgreSQL, которая выбирает способ выполнения запроса: порядок соединений, индексы, алгоритмы                                                           |
| План выполнения               | Дерево операций, которое выбрал планировщик. Показывается командой `EXPLAIN`                                                                                   |
| Узел плана                    | Одна операция в дереве: чтение таблицы, соединение, сортировка. Получает строки от дочерних узлов                                                              |
| `cost` (стоимость)            | Оценка затрат в условных единицах. Нужна только для сравнения вариантов плана, не переводится в миллисекунды                                                   |
| Оценка и факт                 | Оценка (`rows` рядом с `cost`) — прогноз планировщика. Факт (`rows` рядом с `actual`) — реальный результат выполнения при `EXPLAIN ANALYZE`                    |
| Статистика планировщика       | Сведения о распределении данных в столбцах. Собирает команда `ANALYZE`. По ней планировщик оценивает число строк                                               |
| `ANALYZE` и `EXPLAIN ANALYZE` | Разные команды. `ANALYZE таблица` обновляет статистику планировщика. `EXPLAIN ANALYZE запрос` выполняет запрос и показывает его план с фактическими значениями |
| `loops`                       | Сколько раз выполнен узел. Значения `actual` даны на один цикл                                                                                                 |
| Собственное время узла        | Время узла без времени его дочерних узлов. Узел с наибольшим собственным временем — узкое место                                                                |
| Селективность                 | Доля строк таблицы, которую отбирает условие. Малая доля — высокая селективность, индекс полезен                                                               |
| Зависимые условия             | Условия на столбцы, значения которых связаны (город и индекс почты). Планировщик считает их независимыми и ошибается в оценке                                  |
| `CREATE STATISTICS`           | Расширенная статистика по нескольким столбцам. Исправляет оценку для зависимых условий                                                                         |
| Карта видимости               | Отметка страниц, где все строки видны всем транзакциям. Позволяет Index Only Scan не читать таблицу. Обновляется `VACUUM`                                      |
| `Heap Fetches`                | Сколько раз Index Only Scan всё же обратился к таблице: страница не отмечена в карте видимости                                                                 |

**Узлы плана**

| Термин                               | Определение                                                                                         |
| ------------------------------------ | --------------------------------------------------------------------------------------------------- |
| Seq Scan                             | Последовательное чтение всех страниц таблицы                                                        |
| Index Scan                           | Поиск строк по индексу и чтение их страниц в таблице                                                |
| Index Only Scan                      | Чтение данных только из индекса, без таблицы                                                        |
| Bitmap Index Scan + Bitmap Heap Scan | Сначала по индексу собирается список нужных страниц, затем они читаются по порядку, каждая один раз |
| `BitmapAnd` / `BitmapOr`             | Объединение списков страниц от двух индексов по И / ИЛИ                                             |
| Nested Loop                          | Соединение «вложенным циклом»: для каждой строки одного набора ищутся пары в другом                 |
| Hash Join                            | Соединение через хеш-таблицу: один набор загружается в память, строки другого проверяются по ней    |
| Хеш-таблица                          | Структура в памяти для быстрого поиска по ключу без сортировки                                      |
| Merge Join                           | Соединение двух наборов, отсортированных по ключу, слиянием                                         |
| Sort                                 | Сортировка строк                                                                                    |
| HashAggregate / GroupAggregate       | Группировка (`GROUP BY`) через хеш-таблицу / по отсортированному потоку                             |
| Limit                                | Остановка после первых N строк                                                                      |
| `Batches`                            | На сколько частей разбита хеш-таблица. Больше 1 — не хватило памяти, части записаны на диск         |
| `external merge`                     | Сортировка с записью во временные файлы на диске                                                    |
| Материализованное представление      | Результат запроса, сохранённый как таблица. Обновляется командой `REFRESH`. Ускоряет тяжёлые отчёты |

**Параллельное выполнение**

| Термин                            | Определение                                                                                                                                    |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Рабочий процесс (parallel worker) | Дополнительный процесс, который выполняет часть запроса                                                                                        |
| Ведущий процесс (leader)          | Процесс сеанса. Запускает рабочие процессы, участвует в работе и собирает результат                                                            |
| Gather / Gather Merge             | Узел, который собирает строки от рабочих процессов. `Gather Merge` сохраняет порядок сортировки                                                |
| Partial / Finalize                | Два этапа агрегации: частичная в каждом процессе, итоговая в ведущем                                                                           |
| Fetch size                        | Порция строк, которую клиент (например, DBeaver) получает за один раз. При чтении порциями параллельный план выполняется без рабочих процессов |

**Журнал и инструменты**

| Термин                         | Определение                                                                                                                             |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| Журнал сервера (лог)           | Текстовые файлы, куда PostgreSQL пишет события: ошибки, медленные запросы, подключения                                                  |
| `logging_collector`            | Фоновый процесс, который записывает журнал в файлы. Включается только с перезапуском                                                    |
| `log_line_prefix`              | Формат начала каждой строки журнала: время, процесс, пользователь, база                                                                 |
| `lc_messages`                  | Язык сообщений сервера. `C` — английский                                                                                                |
| `log_min_duration_statement`   | Порог в мс: запросы дольше порога записываются в журнал. `-1` — выключено, `0` — все запросы                                            |
| `auto_explain`                 | Модуль, который записывает в журнал план медленного запроса автоматически                                                               |
| `pgBadger`                     | Программа, которая строит HTML-отчёт по журналу PostgreSQL                                                                              |
| Perl                           | Язык программирования, на котором написан pgBadger. В Windows нужен интерпретатор Strawberry Perl                                       |
| Контрольная точка (checkpoint) | Момент, когда все изменённые страницы из памяти записываются на диск                                                                    |
| Автоочистка (autovacuum)       | Фоновая очистка таблиц от мёртвых версий строк                                                                                          |
| `deadlock_timeout`             | Время ожидания блокировки (по умолчанию 1 с), после которого сервер проверяет взаимоблокировку и пишет запись при `log_lock_waits = on` |
